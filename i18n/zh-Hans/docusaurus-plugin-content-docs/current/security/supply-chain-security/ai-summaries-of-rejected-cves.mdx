# 已驳回 CVE 的 AI 摘要

写给所有在漏洞数据之上构建 AI 层的人。

**为已撤回 CVE 生成的摘要会把漏洞描述得仿佛确实存在。** 这种情况并非偶尔发生，也不是因为模型能力不足，而是由记录的结构造成的：撤回信息是一句后补的描述性文字，而其周围的所有结构化内容仍在断言该发现真实存在。

我们在自己的记录中遇到过这个问题。这一模式具有足够的普遍性，值得单独用一页说明，而不是只留在对某一家厂商的投诉中。

---

## 发生原因 {#why-it-happens}

让模型总结一条漏洞记录，它就会总结出一个漏洞，因为这条记录的用途正是承载漏洞信息。标识符被驳回后，承载含义的字段并不会被清空：

- 标题仍然指出一种攻击；
- 严重程度、CVSS 向量和 EPSS 概率仍有数值；
- 受影响产品和版本范围仍然列出；
- 弱点分类及任何映射的攻击模式仍可正常解析；
- 状态字段通常仍显示为 current 或 received 之类的值。

与此同时，撤回信息以替换文本的形式出现在描述字段中。它只是十几项结构化断言中的一条非结构化字符串，也是唯一说明该发现已不存在的元素。

摘要提示词会按照数据的呈现方式权衡这些输入。带评分、带类型且机器可读的字段描述的是一个现存漏洞，因此摘要也会以评估报告般的确信语气描述一个现存漏洞。有些系统还会进一步生成修复建议，告诉读者升级到一个并不存在的修复版本，以解决一个从未真实存在的缺陷。

这种输出并非通常意义上的幻觉。模型只是忠实地总结了记录中仍然保留的内容。

## 两个示例 {#two-examples}

这两个示例都可以直接核查。我们最后一次确认 BaseFortify 示例的日期是 2026-10-30，确认 Vulners 示例的日期是 2026-08-08。

### 撤回通知旁的执行摘要 {#an-executive-summary-beside-the-withdrawal-notice}

在 [BaseFortify](./vulnerability-databases/basefortify.mdx) 上，一条已撤回记录的条目带有 Rejected 徽章，描述中包含 CNA 的驳回通知；同一页面上由 AI 生成的 Executive Summary 却在解释该漏洞如何被利用。对于 CVE-2024-7959，摘要称该缺陷“可被利用来访问内部服务，并可能通过访问实例密钥执行命令”。这两项陈述都清晰可见，彼此并未隐藏。读者会同时看到正确答案和错误答案，而只有错误答案被写成了评估结论。

其周围的结构化字段仍将该记录描述为当前发现：CVSS 基础评分为 7.7 HIGH，EPSS 概率位于第 97.6 百分位，CPE 指向 Open WebUI 0.3.8，攻击流程图则经由 CWE 将该记录映射到 CAPEC。

### 建议升级的生成文本 {#generated-text-that-recommends-an-upgrade}

在 [Vulners](./vulnerability-databases/vulners.mdx) 上，已撤回记录的默认描述由机器生成，并标记为“AI enhanced”。描述称该端点允许未经身份验证的远程攻击者访问敏感配置数据，引用其他数据库作为佐证，最后建议受影响组织升级到已修补版本或采用厂商提供的缓解措施。

没有可升级到的版本，因为根本没有需要修复的问题。同一条目还带有一个生成的风险评分，高于签发 CNA 在撤回记录之前给出的评级。

## 设计要求 {#the-design-requirement}

只需要一项检查，而且应当在生成之前执行，而不是在生成之后。

**先读取记录状态。如果状态为已驳回，就不要生成对该发现的评估。** 要么不生成任何内容，要么只生成撤回信息：该标识符已被驳回、由谁驳回以及何时驳回。

其余要求都由此而来，而且实现成本都不高：

- **不要为已驳回记录评分。** 严重程度、基础评分、向量和利用概率都是在断言漏洞存在。已经没有任何内容可供评级。
- **不要为此类记录生成修复指导。** 升级建议意味着存在修复，而修复又意味着存在缺陷。
- **不要让生成内容在其来源记录失效后继续存在。** 如果摘要是在标识符有效时编写的，状态一旦改变，摘要就会立即过时；之后仍继续提供它，是系统在每次页面加载时作出的选择。
- **将状态公开为字段，而不只是描述性文字。** 下游使用方（包括在你的系统之上构建的下一层 AI）需要可筛选的内容，而不是描述字段中的英文文本。

记录状态很容易获取。任何使用方都可以直接从记录本身读取：

```bash
curl -s https://cveawg.mitre.org/api/cve/CVE-2024-7033 | grep -o '"state":"[A-Z]*"'
```

## 为什么这不只是漏洞数据库的问题 {#why-this-is-not-only-a-vulnerability-database-problem}

只要将模型用于处理漏洞记录，同样的结构就会出现：回答 CVE 相关问题的安全助手、判断发现是否重要的 LLM 分类系统、读取扫描器输出并据此创建工单的代理，以及为下游软件包生成公告文本的依赖工具。

如果它们在检查状态之前生成摘要，就都会继承同一种故障。而且，当其中一个系统发布其输出时，下一个系统就会摄取这些输出；因此，即使原始记录早已沉寂，已撤回标识符仍可能不断获得新的“佐证”。

有关已撤回标识符在各数据库中的一般传播情况，请参阅[漏洞数据库中的已驳回 CVE](./vulnerability-databases/)。
