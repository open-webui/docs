**这是 Open WebUI 针对安全漏洞报告制定的政策：哪些情况属于漏洞、如何报告，以及我们如何处理、署名和发布报告。**

我们的目标是保护 Open WebUI 用户及其数据，并以清晰、一致且公开记录的流程处理安全报告。
我们希望运行透明的安全流程，将已接受的漏洞以公告形式公开发布，让任何人都能了解发现了什么问题、如何解决，以及最重要的是，哪个版本包含相应补丁。
我们的立场是：可见的公告历史证明软件正受到积极审查、披露流程有效运行，而不是衡量软件脆弱程度的指标。

## 受支持的版本 {#supported-versions}

| 版本（分支） | 是否受支持 |
| ---------------- | ------------------ |
| main             | 是 |
| dev              | 否 |
| 其他             | 否 |

**如果你提交时，问题已经修复或已在公开修复过程中，报告将不会被接受。** 该报告没有为发现或修复问题作出贡献，我们也不会为其发布公告。修复内容会列在包含该修复的版本更新日志中。

无论修复位于哪个分支（包括 `dev`），也无论它是否在早期版本中被悄然解决，都视为已有修复。分支支持状态（见上表）决定漏洞必须能在哪里_复现_，而不决定修复是否已经存在：根据此规则，某个缺陷即使仍存在于受支持分支中，但只要已在 `dev` 中修复，就仍属于已修复问题。

此规则明确涵盖以下两种我们均会拒绝的情况：

- 针对**较旧版本**中发现的缺陷提交报告，而当前受支持版本发布时该缺陷已经解决。
- **监控我们的公开提交或拉取请求**，并针对其中已经处理或修复的问题提交报告。我们观察到有人自动监控我们的公开提交和 PR，并针对他人已经编写的修复生成报告；此规则正是用于拒绝这种行为。

你是否独立发现该问题并不重要，我们也无法区分独立发现与抓取公开信息。从可验证的事实看，你的报告是在修复公开后才到达的。无论谁首先发现或修复了该问题，他们都已经公开披露，而没有向我们保密报告，因此同样不会获得署名。任何公开披露的修复都不会为任何人带来署名。

:::tip

**报告之前，请检查你的发现是否仍能在 `dev` 分支**（以及任何其他活跃开发分支）上复现。
我们公开开展开发，修复可能在版本发布前就已提交到这些分支。先确认这一点，可以避免你花费精力撰写一份我们不得不按已修复问题关闭的报告。

:::

## 不构成漏洞的善意报告 {#good-faith-reports-that-arent-vulnerabilities}

**我们真诚感谢每一份善意提交的报告，即使最终根据我们的准则判定它并非漏洞。** 感谢你投入的时间。因超出范围而被关闭的善意报告绝不会对你产生不利影响。

如果你发现的问题**严格来说并不属于我们政策定义的漏洞**，但公开披露仍不负责任（例如，因下游漏洞而需要紧急升级依赖，或类似情况），你仍可以通过 [GitHub Security Advisories](https://github.com/open-webui/open-webui/security/advisories/new) **私下报告**。我们会负责任地处理。

根据 CVE 规则，我们**不会**为这些问题发布公告或申请 CVE，但我们**会**采取行动（例如发布依赖升级），并在处理完成前对报告保密。
<ins>**如果你的报告促成修复落地，并且你希望获得署名，我们会尝试向你致谢（例如将你列为更改的共同作者）。**</ins>

## 有效报告可以获得什么 {#what-a-valid-report-gets-you}

如果你的报告描述了符合本政策的真实漏洞，你可以期待我们提供以下事项：

- **在公告中署名。** 你会在发布的公告中被列为报告者。如果多位报告者分别证明了不同的攻击向量，每位报告者都会获得署名（请参阅[报告处理](#report-handling)）。
- **协调披露。** 在你仍与我们共同处理问题时，我们不会擅自公开。公告本身会清楚显示状态变化（包括 CVE 请求），GitHub 也会向你发送这些更新通知，因此你可以跟进直至发布。
- **负责任地提供真正的修复。** 在 CVE ID 分配之前，详细信息不会公开；目前分配时间约为修复版本发布后四周或更久，以便管理员先行更新（请参阅[预期时间](#expected-timeframe)）。

我们_无法_提供奖金或保证处理时长。你得到的是认真的修复、如实的署名，以及将你的付出视为实际贡献的处理流程。

## 与 CVE 计划保持一致 {#alignment-with-the-cve-program}

**CVE 计划规则**（以及 CNA 运营规则）是此处所有 CVE 处理工作的**基线**，本政策在这些规则内运行。根据这些规则，一份报告是否构成 Open WebUI 中的安全漏洞由厂商判定；本政策记录了我们作出该判定所采用的标准。规则未明确说明的事项仍受规则约束；本政策说明如何将这些规则应用于 Open WebUI 时，其性质是厂商发布的判定标准，而不是对计划规则的替代或例外。

## 在何处以及如何报告安全漏洞 {#where-and-how-to-report-security-vulnerabilities}

:::info

Open WebUI 社区之所以充满活力，正是因为有像你这样深切关注如何让软件对每个人都更安全的人。

为确保你的发现真正帮助保护用户并得到迅速处理，请**仅**通过 [GitHub Security Advisories](https://github.com/open-webui/open-webui/security/advisories/new) 提交所有漏洞报告和 CVE ID 请求。任何其他网站、服务或所谓的“赏金”平台都与我们***没有关联***，你的重要工作将无法送达真正能够作出改变的人。

:::

我们**仅**通过 [GitHub Security Advisories](https://github.com/open-webui/open-webui/security/advisories/new) 接受漏洞报告和 CVE ID 请求。通过**任何**其他平台（包括但不限于第三方漏洞报告平台、漏洞经纪商、社交媒体、电子邮件、Discord 或 Reddit）提交的报告都不会被处理。

我们的安全流程与其他工作一样以透明为核心，[GitHub Security Advisories](https://github.com/open-webui/open-webui/security/advisories/new) 是承载这一流程的唯一权威渠道。我们不会也无法监控外部报告平台或与其互动，通过这些平台提交的报告将不经审查直接关闭。

在其他平台提交的报告或 CVE ID 请求在这里不具有效力。它不会带来任何优先级、不构成提交日期，也不会使我们负有分类、发布或以其他方式考虑它的义务。就本政策而言，只有 GitHub Security Advisory 记录有效，包括用于判定谁先提交。

## 威胁模型 {#threat-model}

Open WebUI 是一个**自托管、单租户、需要身份验证、基于角色**的应用程序。报告在这一模型下评估：

- **用户必须经过身份验证**，才能访问任何用户数据或产品功能。按照设计，浏览器在登录前所需的端点（登录、注册以及登录界面读取的公共配置）无需账户即可访问。
- **管理员受信任**，并拥有完整系统控制权。同一实例的管理员共享同一个信任边界。
- **安全设置采用默认值或更严格的配置。**
- **Tools、Functions 和 Pipelines 按设计会执行任意代码。** 管理员控制谁可以创建它们。

## 报告准则 {#reporting-guidelines}

感谢社区对识别潜在漏洞的关注！
如果你想报告的内容不符合这里列出的规则和准则，仍可通过 [GitHub Security Advisories](https://github.com/open-webui/open-webui/security/advisories/new) 提交，我们会进行处理。更多信息请参阅[善意报告部分](#good-faith-reports-that-arent-vulnerabilities)。

我们**不**接受低质量、低投入的漏洞报告。请确保**提交内容具有建设性和可操作性、可以复现、文档充分，并遵循以下准则**：

**安全边界：** 在本政策中，“安全边界”指我们认可的五项边界：机密性、完整性、可用性、真实性和不可否认性。我们对其作广义解释：其他安全框架中的等同概念也属于这些边界。有效漏洞必须针对报告者以外的一方越过其中至少一项边界。

1. **报告必须描述漏洞：** 安全漏洞是一种可被利用的弱点，系统会因此以非预期方式运行，使攻击者能够绕过安全控制、获得未经授权的访问、执行任意代码或提升权限。配置选项、缺失的功能和预期的协议行为不属于漏洞。漏洞必须越过至少一项安全边界（定义见上文）。

2. **不接受含糊的报告：** “我发现了一个漏洞”之类没有任何细节的提交会被视为垃圾信息，不予接受。

3. **深入理解：** 报告必须体现对代码库和 Open WebUI 使用方式的清楚理解，并提供漏洞的具体细节，包括受影响组件和潜在影响。

4. **必须提供概念验证（PoC）：** 每份提交都必须包含文档充分的概念验证（PoC），用于演示该漏洞。如果担心机密性，建议报告者创建仓库的私有分支，并在公告中与维护者共享访问权限。缺少有效证据的报告可能不予考虑。

:::note

PoC（概念验证）是对**漏洞利用过程的演示**。你的 PoC 必须展示：

1. 究竟越过了哪项安全边界
2. 如何触发/滥用此漏洞（输入、端点、UI 操作等）
3. 攻击者现在可以执行哪些操作
4. 确切的复现步骤和命令（尽可能可直接复制/粘贴运行），以及预期结果与实际结果

:::

5. **默认配置测试：** 漏洞报告必须使用 Open WebUI 开箱即用的默认配置进行测试并可复现。只有在明确削弱安全设置后才会出现的漏洞声明可能被驳回，除非符合以下例外：

:::note

如果你认为自己发现的安全问题符合以下任一情况：

1. 影响默认配置，**或**
2. 真正绕过了预期的安全控制，**或**
3. 仅在非默认配置下有效，**但相关配置很可能用于生产部署**，**那么我们非常希望你报告。** 本政策旨在过滤配置问题和部署问题，而不是阻止合理的安全研究。

:::

6. **必须理解威胁模型：** 报告必须体现对 Open WebUI 自托管、单租户、需要身份验证、可扩展、基于角色的访问控制架构的理解。如果将 Open WebUI 与安全模型根本不同的服务进行比较，却不承认架构差异，报告可能会被拒绝。

7. **CVSS 评分准确性：** 报告中不必须包含 CVSS 评分。如果你将 CVSS 部分留空，我们会在发布前为你填写。如果报告中包含 CVSS 评分，则必须按照 CVSS 方法准确反映漏洞。如果 CVSS 不准确，我们会调整报告的 CVSS 评分。如果引用其他 CVE 支持你的报告，请确保它们在漏洞类型、威胁模型和攻击向量方面**确实具有可比性**。

8. **管理员操作不在范围内：** 需要管理员主动执行不安全操作的漏洞**不被视为有效漏洞**。**管理员拥有完整系统控制权，应当理解其操作和配置的安全影响。** 这包括但不限于：添加恶意外部服务器（模型、工具、webhook、应用、函数）、将不可信代码粘贴到 Functions/Tools 中，或故意削弱安全设置。**需要管理员疏忽或对管理员实施社会工程学的报告可能会被拒绝。**

:::note

与“默认配置测试”规则类似：如果你认为自己发现的漏洞会影响管理员，且并非由管理员疏忽或故意恶意行为导致，
**那么我们非常希望你报告。** 本政策旨在过滤针对管理员的社会工程攻击、管理员部署恶意插件及类似恶意行为，而不是阻止合理的安全研究。

:::

9. **Tools 和 Functions 的代码执行属于预期行为：** Tools 和 Functions 在服务器上执行用户提供的 Python 代码，其访问权限与 Open WebUI 后端相同。这是核心且符合预期的功能（请参阅“理解威胁模型”）。只有管理员可以创建 Functions。创建 Tools 需要 `workspace.tools` 权限，该权限对非管理员用户默认关闭。<ins>**授予此权限等同于授予服务器的 shell 访问权限**</ins>，因此将其授予不受信任的用户属于“管理员操作不在范围内”所涵盖的错误配置。**描述通过 Tools 或 Functions 形成的任何攻击链（代码执行、文件访问、网络请求、环境变量访问、front matter 中的 `pip install` 等）的报告，都会按预期行为关闭。** 不需要这些功能的部署可以通过 [`ENABLE_PLUGINS`](/reference/env-configuration#enable_plugins) 和相关开关将其关闭。

10. **旧版代码路径不在范围内：** Open WebUI 保留了一些在官方文档中明确标记为旧版的代码路径，哪些路径属于旧版以官方文档为准。保留旧版路径（有时它们仍是默认路径）纯粹是为了向后兼容，并不表示它们是受支持或维护的接口。受支持的替代方案才是迁移目标，安全和功能工作会针对替代方案，而非旧版路径。如果报告描述的安全边界问题仅存在于旧版代码路径，而无法在受支持的替代方案上复现，那么根据此规则通常不在范围内。

:::note

如果你发现的安全问题符合以下任一情况：

1. 同时存在于旧版代码路径**和受支持的现代替代方案**，或
2. 存在于旧版代码路径，**且该旧版路径是文档中实现某项功能的唯一方式**（尚无迁移目标）

我们仍希望你报告。此规则旨在过滤针对已有现代替代方案的弃用路径报告，而不是阻止大家在用户仍在使用的路径中发现真实缺陷。

:::

11. **AI 报告透明度：** 如果 AI 以任何方式提供了帮助，请告诉我们，包括发现漏洞、撰写报告或构建 PoC。AI 辅助报告的处理方式与其他所有报告完全相同；我们只是希望知情。

12. **仅影响自身的问题不属于漏洞：** 漏洞必须越过安全边界并影响**报告者以外的一方**。如果越过安全边界只影响报告者自己的数据、账户、会话或环境，则**不属于漏洞**；它是一个缺陷，应提交到 [Issue Tracker](https://github.com/open-webui/open-webui/issues)，而不是作为安全报告。

:::note

此规则关注的是**谁受到损害**，而非严重程度。根据此规则，用户修改或删除自己的数据、损害自己的会话、查看自己的配置，或禁用自己账户上的安全控制，无论影响如何都不在范围内。

如果同一操作还影响其他用户、运维人员、主机系统或共享资源，请在 PoC 中明确指出受影响的第二方，我们希望你报告。

:::

不遵循这些准则的提交可能会被关闭。只有反复或故意无视准则的报告者才可能被禁止提交报告；无意的错误和善意报告绝不会计入其中。我们的目标是营造建设性的报告环境，让高质量提交促进所有用户的安全。

## 预期时间 {#expected-timeframe}

安全报告与所有其他项目工作一起排定优先级，而且报告数量非常多。从报告被查看、分析、分类到修复，**预计需要数周**，期间可能会有数段没有消息的时间。**没有消息并不意味着你的报告被忽视**；它只是尚未被领取处理。如果你认为报告被遗漏，可以在公告中发布跟进评论。

修复发布后，我们会向 GitHub 请求 CVE ID，并在分配后尽快发布公告。GitHub 目前需要**约四周或更久**来分配 ID；关于我们为何等待，请参阅[发布前分配 CVE](#cve-assignment-before-publication)。即使 GitHub 加快分配速度，对于具有广泛或严重实际影响的发现（无论 CVSS 评分如何），仍会等到修复版本发布约两周后再公开，以便管理员更新。

**本页中的所有时长均为估计值。** 条件顺利时报告可能处理得更快，遇到阻碍时则可能更慢。

**我们不接受报告者单方面设定的发布期限。** 我们按照自己的时间表协调披露，并会在合理范围内尽快分类、修复和发布。外部强加的硬性期限不会加快这一进程，反而会产生相反效果：它们会把我们的时间从实际修复问题转移到管理倒计时上，**代价是牺牲队列中所有其他报告（包括可能更严重的报告）和整个项目**。报告附带的期限不会改变其处理时间或速度。

## 发布前分配 CVE {#cve-assignment-before-publication}

**我们只在 GitHub 分配 CVE ID 后才发布安全公告。** GitHub 是我们通过 GitHub Security Advisories 所申请 CVE 的 CVE 编号管理机构（CNA）。公告修复并准备就绪后，我们会申请 CVE，公告会保持未发布状态，直到 ID 分配完成。按 GitHub 当前的分配速度，<ins>**这会将每份 Open WebUI 公告的发布时间推迟约四周或更久。**</ins>

**在此规则实施前**，我们会请求 CVE 并立即发布公告。问题已在版本中修复，而发布公告可以告知管理员哪些版本受到影响：公告会进入 GitHub Advisory Database 并触发 Dependabot 警报。CVE ID 则由 GitHub 稍后添加。

**发生了什么。** 2026 年 9 月 27 日和 28 日，我们以这种方式发布了 19 份公告，CVE 请求在 GitHub 等待了数周。2026-10-12，另一个 CNA——VulnCheck——为全部 19 个问题发布了自己的 CVE 记录，随后 GitHub 以重复为由拒绝了我们的请求。我们认为，代码所有者通过 GitHub Security Advisories 请求的 CVE 属于 GitHub 的范围；GitHub 和 VulnCheck 则认为，只有在没有其他 CNA 的范围涵盖该问题时，GitHub 的范围才涵盖它。无论如何，**在记录分配前没有任何一方联系我们。** 协调披露依赖 CNA 在分配前联系厂商，而 VulnCheck 没有这样做。它的记录将我们公告的标题替换为 VulnCheck 自己的标题，公告至今仍在使用这些标题；19 份记录中有 16 份列出了错误的署名，另有数份列出了错误的弱点类型或评分，直到我们提出异议后 VulnCheck 才予以更正。进入 GitHub Advisory Database 的副本更糟：条目未经审查，标题是描述在半句话处被截断的内容，没有生态系统、没有受影响的软件包，也没有受影响或已修复的版本。它们从未触发过任何 Dependabot 警报，因此运行受影响版本的管理员从未收到过这些警报。

**我们不接受其他 CNA 为 Open WebUI 签发 CVE**，因为我们无法依赖它们生成正确记录：我们的[厂商判定](./vendor-dispositions/)列出了其他 CNA 签发且不得不被拒绝的记录，VulnCheck 的 19 份记录也存在上述错误。GitHub 分配的 CVE 基于我们编写的公告，并作为经过审查的条目进入 GitHub Advisory Database，包含受影响的软件包和版本，因此 Dependabot 可以从公告发布之日起提醒每个受影响的部署。等到 GitHub 分配 ID 后再发布，就不会留下让其他 CNA 抢先签发的窗口。公告会晚几周到达管理员手中，但内容完整，没有缺失信息，数据和元数据正确，并由我们、报告者和作为 CNA 的 GitHub 共同编写和核验。

## 报告处理 {#report-handling}

当多位独立报告者描述同一类漏洞，**但**各自证明了**不同且独立的利用向量**（例如，通过不同端点触及同一个缺失的授权检查）时，我们会将这些报告合并到最早的提交中，**并在合并后的公告中为每位证明不同路径的报告者署名**。合并后的公告只会签发一个 CVE。

另一种情况是：如果你报告的有效漏洞已由他人先于你报告（漏洞完全相同、利用向量完全相同），我们会将你的报告作为重复项关闭。此后我们会处理最早的提交，不会为同一漏洞发布多份公告。

### 为什么重复报告不获得署名 {#why-duplicate-reports-dont-receive-credit}

对于同一漏洞，我们只为最早的提交者署名：

1. **第一份报告完成了实际工作。** 后续报告到达时，分类和修复已经开始。后续报告不会改变结果或时间表；为它们署名会错误反映是什么推动了修复。
2. **为重复报告署名会鼓励灌水。** 如果相似但更晚的提交也能获得署名，理性做法就会变成浏览公开公告并提交各种变体。我们已经看到这种压力，而最早提交者规则正是限制它的措施。
3. **不同的发现确实可以共享署名。** 如果你的报告增加了较早提交未涵盖的内容（不同向量、不同受影响组件或不同子路径），**你会与第一位报告者一起在同一份公告中获得署名**，如上述合并规则所述。只有报告完全相同的问题才算重复。

## 保密披露 {#confidential-disclosure}

通过 GitHub Security Advisories 提交的漏洞报告属于**私密和保密信息**。一般而言：在漏洞公告**完整发布**之前，**严禁**公开披露**任何**细节；完整发布是指公告本身已公开可见。仅分配 CVE ID 并不足够。

这项禁令适用于**所有渠道和所有第三方**，包括但不限于：

- 在 GitHub 或其他地方的拉取请求、议题或讨论中发表评论；
- 社交媒体、聊天服务器和论坛（Discord、Reddit、X 或任何其他平台）；
- 博客、分析文章、演讲、论文和新闻通讯；
- 邮件列表、漏洞数据库、漏洞赏金平台和漏洞经纪商；
- 任何其他组织，包括向其请求该问题的 CVE ID 或任何其他标识符；
- 任何其他网站或服务。

这一保密、负责任的披露流程旨在为我们争取时间修复缺陷、发布修复，并在修复准备就绪后提醒用户。负责任披露的全部前提是**保护用户免受漏洞伤害**。因此，过早披露会损害所有 Open WebUI 用户的安全，并**违背负责任披露流程所基于的信任**。 **在官方发布前过早公开披露漏洞细节的报告者，<ins>将被永久禁止提交后续报告。</ins>**

## 第三方 CNA 与厂商判定 {#third-party-cnas-and-vendor-disposition}

[基于第三方 CNA 多次在发布前未与我们沟通报告便签发 CVE，和/或签发的 CVE 经不起任何审查的先例](./vendor-dispositions/)，我们制定了此规则。
当报告通过 GitHub Security Advisories 提交，而维护者根据本政策将其作为超出范围关闭时，此次关闭就是厂商对该问题的**判定**。CNA 为这类问题签发 CVE，却未在相应记录中体现该厂商判定，就属于违背厂商判定的行为。

我们会通过以下方式应对此类记录：

1. 向 CVE 计划提交 **REJECT** 请求（以 **DISPUTED** 作为后备）；
2. 在我们的[厂商判定](./vendor-dispositions/)中公开收录该记录，并指明签发 CNA；
3. 拒绝提供厂商声明、版本映射、修复参考或任何其他会为该记录赋予权威性的协调配合；
4. 将单个 CNA 反复出现的行为上报至 CVE Program Root。

**遵守渠道要求并不意味着 CNA 有权推翻厂商判定。** 在厂商判定发布后，报告者若将已按超出范围/非漏洞关闭的 GHSA 报告升级至第三方 CNA，也会被视为违背厂商判定，**并可能被禁止后续提交 GHSA。** 如果你不同意关闭决定，请在公告中回复并提供新证据。出现新信息时，我们会重新评估已关闭的报告，并完全愿意重新开启。

此规则之所以存在，是因为这类升级行为的成本并不对称。标识符可以在几天内签发，而移除不准确的标识符需要在签发 CNA、CVE 计划以及镜像该记录的每个下游数据库之间进行长达数月的沟通，这些工作却不会由创建记录的一方承担。我们的判定以及与其他 CNA 的争议表明，我们无法依赖第三方 CNA 遵守 CNA 规则或在分配标识符前核实报告。完整理由以及这些升级行为实际造成成本的记录，请参阅 [CVE 系统以及本页面存在的原因](./vendor-dispositions/#the-cve-system-and-why-this-page-exists)。

## Tools、Functions 和 Pipelines 安全 {#tools-functions-and-pipelines-security}

**Tools、Functions 和 Pipelines 会在你的服务器上执行任意 Python 代码**，其访问权限与 Open WebUI 后端相同，包括文件、网络、子进程、环境变量和数据库。这是刻意设计。有关它们的报告按[报告准则](#reporting-guidelines)第 9 条处理。已能写入数据卷（安装插件的存储位置）的攻击者同样超出威胁模型。安全使用方法请参阅[插件安全](/features/extensibility/plugin/)警告和[加固指南](/getting-started/advanced-topics/hardening#tools-functions-and-pipelines)。

## 生产部署安全 {#production-deployment-security}

Open WebUI 面向私有、受信网络设计，默认设置以易于安装为优化目标。处理敏感数据的生产部署应查看[加固指南](../getting-started/advanced-topics/hardening.md)，获取完整检查清单。

一个关键注意事项：**没有 Redis 时，退出登录不会撤销该会话的 JWT 令牌**。令牌在过期前（默认：4 周）一直有效。无论是否使用 Redis，更改密码和管理员的**退出所有设备**都会结束账户的所有会话。对于生产部署，请配置 [Redis](../tutorials/integrations/redis.md)，或缩短 `JWT_EXPIRES_IN`，以限制暴露窗口。详情请参阅[令牌撤销](../getting-started/advanced-topics/hardening.md#token-revocation)。
