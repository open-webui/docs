# 身份验证计时侧信道

|  |  |
| :--- | :--- |

| **状态** | 可被利用的信号已缓解；亚毫秒级剩余差异已接受 |
| **跟踪编号** | [GHSA-7rw5-9f7q-xj36](https://github.com/open-webui/open-webui/security/advisories/GHSA-7rw5-9f7q-xj36) |

## 概述 {#summary}

登录端点处理已存在账户的耗时明显长于不存在的账户，因为只有账户存在时才会验证密码哈希。这一差异（约为 150&nbsp;ms 与 5&nbsp;ms）使攻击者能够根据响应时间枚举有效账户，并可能为后续的密码喷洒攻击提供目标。

## 我们已缓解的风险 {#what-we-mitigated}

该问题已报告给我们，并以 [GHSA-7rw5-9f7q-xj36](https://github.com/open-webui/open-webui/security/advisories/GHSA-7rw5-9f7q-xj36) 跟踪。我们已在登录路径中处理该问题：现在，对于找不到用户或找不到有效凭据的路径，身份验证会针对固定的虚拟哈希执行 bcrypt 比较。因此，无论账户是否存在，每次登录尝试都会产生相同的 bcrypt 开销。

实测表明，这一差异已从约 20–40 倍缩小到约 1.03 倍（bcrypt 与 bcrypt），与正常的逐次运行波动无法区分。实际可利用的账户枚举预言机已被消除。对于默认的 bcrypt 哈希，这种开销均衡有效；使用 `PASSWORD_HASH_ALGORITHM=argon2` 时，密码存储为 argon2 哈希的账户会执行 argon2 验证，而不存在的账户会执行虚拟 bcrypt 验证，因此两者的开销会再次出现差异。登录还限制为每个电子邮件地址每 3 分钟最多尝试 15 次（未使用 Redis 时按进程计数），这可以限制针对任何单个账户的暴力猜测，但无法限制跨多个账户的密码喷洒。

剩余的毫秒级差异按现状接受。继续投入精力也无法消除它：剩余差异受物理和运行时限制（数据库、Python 解释器、CPU 行为、操作系统调度和网络抖动）约束，而非 Open WebUI 代码可以改进的部分，因此继续缩小差异的收益已非常有限。相关理由见下文[剩余风险及为何无法修复](#what-remains-and-why-it-is-not-fixable)。

## 剩余风险及为何无法修复 {#what-remains-and-why-it-is-not-fixable}

应用层代码无法实现完全恒定时间的身份验证。一旦主要的 bcrypt 开销达到一致，剩余差异就会低于一毫秒，并由 Open WebUI 无法控制的层产生：

- **数据库查询**（已存在的电子邮件会命中索引，不存在的电子邮件则无法命中），
- **Python 解释器和垃圾回收器**，
- **CPU 行为**：缓存状态、分支预测、推测执行，
- **操作系统调度**，
- **网络抖动**。

这些都无法通过 Python 完全降为零。固定时间填充（“始终在设定的时间窗口内响应”）也无法消除差异：时间窗口必须按最坏情况填充，这会拖慢每次正常登录，而且足够精确的攻击者仍然可以观察到填充开始前完成的工作。它用真实且永久的性能代价，换来一种问题已经彻底解决的错觉。

剩余信号低于一毫秒，且主要被网络和调度噪声掩盖，因此无法通过网络进行可靠测量。因此，我们将其作为已知限制接受，而不视为可修复的缺陷。
