# 智能体应用风险

|  |  |
| :--- | :--- |
| **类别** | 智能体系统的固有行为（目标劫持、工具滥用、记忆与上下文投毒、欺骗性或失控的多智能体行为），对应 OWASP 智能体应用十大风险 |
| **状态** | 自主 AI 智能体所固有；其本身不是可修复的应用程序缺陷；除非根据[安全政策](../security-policy.mdx)被证明与真实的 Open WebUI 漏洞构成攻击链，否则不属于漏洞范围 |

---

## 概述 {#summary}

Open WebUI 尊重并感谢 [OWASP 智能体应用十大风险](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)；它是分析自主、可使用工具的 AI 系统如何失效的重要框架。然而，其中记录的许多行为并非传统意义上的安全漏洞。它们是赋予语言模型自主行动能力所固有的风险，存在于任何允许模型规划、使用工具和行动的应用中，而非由特定厂商代码中的缺陷引入。这些风险直接建立在 [LLM 输出的不可预测性](./llm-output-unpredictability.mdx)所介绍的模型层行为之上，而且两者高度重叠：智能体就是拥有工具和自主权的语言模型，因此会产生不安全输出的同一种可引导性，也会驱动不安全的行动。

智能体系统会规划、决策、调用工具，并在不同步骤之间保留上下文，而这一切都以不可信的自然语言输入为依据。因此，精心构造的提示词、被投毒的文档或网页、欺骗性的工具输出，或来自其他智能体的消息，都可能引导智能体追求被劫持的目标、滥用已获授权的工具、依据被投毒的记忆行动，或说服人类批准本不应批准的事项。这些是自主 LLM 智能体工作方式的固有属性，**并非 Open WebUI 代码中的缺陷**。

## 我们缓解的风险 {#what-we-mitigate}

Open WebUI 的职责是提供平台，并控制智能体*被允许*执行的操作。我们的有效控制措施包括用户授权的权限、特权限制、访问控制和隔离：

- **能力须获授权，而非默认授予。** 智能体通过工具执行操作。创建 Tools 需要管理员角色或 `workspace.tools` 或 `workspace.tools_import` 权限；对于非管理员，这两项权限均**默认禁用**。使用某个 Tool 需要拥有该 Tool 的访问权限，而 Function 的编写仅限管理员。授予上述任一权限即等同于向该用户授予服务器的 shell 访问权限（请参阅[安全政策](../security-policy.mdx)第 9 条）。
- **智能体不能超越调用用户自身的权限。** 代表用户行动时，它受该用户的角色、RBAC 权限和按用户划分的数据范围约束；它无法读取或访问用户无法通过 Open WebUI 自身 API 读取或访问的内容。Tool 或 Function 中的 Python 代码以后端进程的访问权限运行，因此编写它们会被视为拥有 shell 访问权限。
- **执行隔离。** 服务器端代码执行需要主动启用并由管理员配置；在生产环境中，[Terminals 编排器](/features/open-terminal/terminals)会在容器隔离的实例中运行代码，并设置资源限制。
- **运维人员防护措施。** [Filters](/features/extensibility/plugin/functions/filter)、人工介入确认（工具权限，由 [`ENABLE_TOOL_PERMISSIONS`](/reference/env-configuration#enable_tool_permissions) 控制且默认关闭，因此工具调用不会询问）和内容检查，让部署能够围绕智能体可执行的操作添加自己的策略层。

这些控制措施可以限制被引导或行为异常的智能体所造成的*后果*，但无法也不可能确保自主智能体的决策在任何情况下都可靠且安全。

## 剩余风险及为何不视为漏洞 {#what-remains-and-why-it-is-not-treated-as-a-vulnerability}

如果一项风险的全部影响都是**智能体表现出其固有的行为能力**（目标被劫持、记忆被投毒、在已获授予的权限范围内不安全地使用工具、人类被自信的智能体说服），那么它就是**自主智能体所固有的风险，其本身不是 Open WebUI 漏洞**。它受限于模型和智能体对齐技术的当前水平，而非 Open WebUI 代码可以修补的问题。

因此，**如果报告的全部影响只是智能体被说服滥用其本已获准使用的能力，或在已授予的范围内产生不良输出或行动，我们不会将其作为漏洞接受。** 这是运行自主智能体时一种已接受的固有属性。

**这是关于智能体行为的范围界定，并非一刀切的豁免。** 一旦精心构造的输入从“智能体受到引导”演变为 Open WebUI 自身代码或控制措施中的具体缺陷，该报告**就**属于范围，并会被视为真实漏洞，例如：

- 智能体的某项操作**提升了权限、访问了其他用户的数据，或通过 Open WebUI 代码路径获得代码执行能力**，而非使用运维人员授予的能力；
- **绕过访问控制、权限或隔离检查**（例如工具访问调用用户无权访问的数据）；或
- 智能体仅是底层应用程序缺陷的**触发因素**的任何漏洞。

这些都是 Open WebUI 缺陷，并会按缺陷进行修复。这一区分与框架自身的界定一致：智能体严格在已授予权限内滥用工具属于固有的智能体风险，而通过平台缺陷提升权限或执行代码则属于缺陷。完整的报告范围请参阅[安全政策](../security-policy.mdx)。

### 判断依据是缺陷所在，而非由谁触发 {#the-test-is-where-the-defect-lives-not-who-triggered-it}

上述排除范围取决于工具的实现，而非智能体对工具的使用方式。简而言之：**如果工具执行了我们未预期的操作，那才是缺陷，滥用它的智能体并不是缺陷。**

可从以下两种情况理解。

- **工具按设计运行，而智能体将其用于我们不希望的用途。** 这属于智能体风险，无论结果多么出人意料或代价多么高昂，都不在漏洞范围内。工具完成了其设计用途；未限制智能体使用工具的频率或强度是配置与加固问题，而非缺陷。
- **工具本身执行了我们未预期的操作，例如随附的内置工具缺少访问检查，而智能体通过它访问了数据。** 缺少检查就是漏洞。智能体只是触发因素，与上述第三种情况完全相同。

这也是上述排除范围针对 Open WebUI 随附工具的原因：对于这些工具，预期行为由我们定义，并可对照我们的代码检查。对于用户自行编写或导入的工具，不存在这种非预期绕过，因为工具的行为由其作者定义，而创建或导入工具的权限本身就等同于 root 权限。
