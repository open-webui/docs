# 参与贡献

**助力打造人人应得的 AI 界面。**

Open WebUI 是一个由小型专职核心团队构建和维护的独立项目。最有价值的贡献方式包括测试开发版本、提交清晰的缺陷报告、在 Discussions 中说明使用场景、改进文档以及翻译界面。维护者会在内部评估和开发代码变更；**代码拉取请求必须获得维护者的明确邀约**，但仅限于 i18n/本地化的变更除外。本页介绍如何参与以及需要了解的事项。

---

## 行为准则 {#code-of-conduct}

所有贡献者和社区参与者都必须遵守**[行为准则](https://github.com/open-webui/open-webui/blob/main/CODE_OF_CONDUCT.md)**。我们实行**零容忍政策**：不尊重他人、强索强求或敌对的行为会立即受到处理，不事先警告。

Open WebUI 由一个小型核心团队领导，并得到整个项目贡献者的支持。请以专业、尊重的态度对待每一次互动。

---

## 贡献方式 {#ways-to-contribute}

### 测试开发分支 {#test-the-development-branch}

最有价值的贡献之一完全不需要编写代码。运行 dev 分支，在日常生活中使用它，并报告出现的问题。

```bash
docker run -d -p 3000:8080 -v open-webui:/app/backend/data --name open-webui ghcr.io/open-webui/open-webui:dev
```

dev 分支变化很快，因此请**定期拉取更新**。如果你不想使用 Docker，请改为遵循[开发 Open WebUI](/getting-started/advanced-topics/development) 中的说明。

在 [GitHub](https://github.com/open-webui/open-webui/issues) 上报告问题时，请提供清晰的复现步骤。社区测试有助于我们交付高质量的版本。

### 提交代码 {#submit-code}

我们在内部开发和改进解决方案，因为外部实现通常需要大量返工才能融入项目。**只有在我们明确发出邀约，或者变更仅限于 i18n/本地化时，我们才会接受代码 PR。** 无论补丁大小、检查是否通过、代码由人工编写还是借助 AI 编写，这项要求都适用于缺陷修复、功能、重构、依赖变更、界面变更以及仅涉及测试的变更。缺陷得到确认或想法获得积极回应，并不等于邀约实现。未遵循此流程提交的 PR **通常会未经审查直接关闭**。

**我们会关注并核实每一个 issue**，而且**内部通常已经有可行解决方案**，只是在评估和完善方案期间尚未推送。某个 issue 一直处于打开状态、没有公开回复或关联 PR，并不表示它未受关注，也不表示实现工作可以认领。可行的修复仍须符合项目架构、现有行为和正在进行的工作。这项评估经常会改变解决方案的范围和位置：界面中的症状可能源于共享状态、API 约定或特定提供方的行为，而一项新设置可能在满足某个工作流的同时损害其他工作流。解决眼前症状只是工作的一部分。公共仓库的活动无法展示每一项正在进行的调查或实现，而未经邀约的 PR 往往会重复已经在开展的工作，同时引入另一种需要协调的方案。维护者需要留出完成评估的空间，然后再发布结果。

明确邀约要求确定了由谁决定哪些实现工作可以进入项目以及何时进入。未经邀约的 PR 到来时，范围、设计和一系列取舍已经固化在代码中，而维护者尚未就这些是否应为项目所作的决策达成一致。审查这类 PR 会把开放的设计问题变成围绕既有实现的协商。随后，作者已经投入的心血会形成保留该方案的压力，即使正确结果应当采用不同设计、缩小变更范围或完全不增加功能。我们需要根据项目需求作出这些决策。维护者发出邀约，表明我们已经确定有价值的外部工作，并且**在有人投入之前，已就其目的和范围达成一致**。

正因如此，**即使代码十分出色，这项要求也同样适用**。如果每个未经邀约的 PR 都能以可能有用为由获得审查资格，我们就必须实际完成审查，才能判断这项要求是否适用。这样一来，提交规则便失去了意义。我们不会为独立选定的实现设立通用审查队列。我们根据项目优先级选择工作，并在有助于推进这些工作时邀约贡献。整洁的 diff、通过的检查或愿意修改的承诺，都不能替代这一决策。即使具备审查能力，这仍然是我们的开发流程。

审查外部实现、解释所需变更并协调连续多轮修改，**通常比在内部开发解决方案更耗费精力**。零散的提交历史、未变基的 branch、未解决的冲突、无关编辑以及未经验证的 AI 生成说明，都会进一步增加工作量。维护者仍须重建其中的假设、评估更广泛的影响，并充分理解最终实现以便对其负责。这些工作需要投入与处理回归、安全修复和版本发布相同的注意力。这项要求可防止计划外的实现审查决定这些注意力的分配。

**代码一经发布，团队就要对其在未来版本中的行为负责。** 我们必须在需要时保持兼容性、诊断故障、维护文档和回归测试覆盖，并随着周边系统演进调整变更。每个新依赖、设置和抽象都会增加这份责任，用户也会围绕我们接受的行为构建工作流。日后移除不合适的变更，也会带来兼容性和迁移成本。对这些后果负责的人，必须在实现开始前决定项目要承担哪些承诺。杰出工作由维护者主动考虑；贡献者不应将自己对补丁的评估视为绕过流程的许可。

**新增或重写自动化测试也需要明确邀约**，包括测试夹具、快照和测试基础设施。邀约实现修复并不包含邀约添加测试套件。当代码和测试基于相同的假设生成时，二者可能相互吻合，却都不符合预期行为。根据当前输出得出的断言可能保留错误；mock 可能移除发生故障的集成环节；快照可能记录错误结果。绑定内部函数调用的测试可能妨碍合理重构，却无法发现影响用户的回归。**让这类测试通过会制造虚假的安全感**，而更多断言和更高覆盖率并不能说明是否检查了正确的行为。

这些测试会成为另一套需要调查、重写和维护的实现。在依赖它们之前，我们必须核实其预期结果、假设以及检测原始故障的能力。维护者会在确立预期行为后，在内部选择可持续的回归测试覆盖方式，并在符合该计划时邀约外部测试工作。对于受邀约的 PR，**请提供来自运行中应用的可复现证据**：包括设置、确切步骤、预期行为，以及变更前后观察到的结果。附上相关日志、截图或录像，运行与变更相关的现有检查，并报告失败项以及所有无法验证的内容。不得为了让变更通过而删除、禁用或弱化现有测试。无论人工验证还是测试套件通过，都不能取代对方案及其广泛影响的审查。

**公开源代码和接收贡献是项目作出的两项独立决策。** [SQLite 将自己描述为“开源，但不开放贡献”](https://www.sqlite.org/copyright.html)：其限制用于维护代码的公共领域状态，其文档也说明概念验证补丁可以从零开始重写。SQLite 有一套接受贡献代码的正式流程。二者的相似之处在于，有用的报告和参考实现可以为解决方案提供信息，而维护者仍掌握发布内容的控制权。Open WebUI 的考量涉及开发能力、架构一致性和长期责任；SQLite 的公共领域要求则是 SQLite 特有的要求。

[tldraw 在 2026 年 1 月发布的政策公告](https://github.com/tldraw/tldraw/issues/7695)提到关闭外部 PR，并有选择地重新开放正在考虑的工作，其理由包括 AI 生成的提交、上下文不完整以及作者后续跟进有限。其[贡献指南](https://github.com/tldraw/tldraw/blob/main/CONTRIBUTING.md)引导人们前往 issue 和 branch 引用，同时声明不接受贡献。[Clojure 的开发政策](https://clojure.org/dev/dev)通过自己的流程接受补丁，但将方向决策交由核心团队负责，并要求功能提案在进入实现之前先明确问题并比较替代方案。这些是不同的政策，具有不同的治理和许可安排。它们展示了社区意见如何为项目提供信息，同时由维护者决定项目的设计和贡献流程。Open WebUI 仍为明确邀约的工作和本地化贡献保留参与途径。

**如果你真心希望帮助 Open WebUI，就应以项目需求以及维护者能否依据你的贡献采取行动来衡量其价值。** 精确的复现、经过深入调查的报告或对工作流的有用说明，都可以改进项目，而不必以你的名义合并一个 PR。请做好准备：维护者可能用不同方式解决问题、在内部实现解决方案，或认定某项提议的变更不属于项目。**帮助项目意味着，即使你的代码未被采用，也要支持这样的结果。** 请通过 [Issues](https://github.com/open-webui/open-webui/issues) 提交可复现的缺陷，通过 [Discussions](https://github.com/open-webui/open-webui/discussions/new/choose) 提交提案。搜索已有报告，检查当前发布版本和 `dev`，并提供受影响的工作流、预期与实际结果以及相关证据。安全问题请通过[私密安全报告流程](https://github.com/open-webui/open-webui/security)报告。如果实现说明、本地 diff、补丁或 branch 引用有助于澄清问题，请在相关报告中分享；不要为了吸引他人关注参考代码而提交 PR。请继续提供有用证据，并尊重团队优先级。报告并不保证一定得到回复、实现或时间表，反复催促或重复提交会占用处理实际工作的时间。

当我们邀约 PR 时，目的是完成项目已确认需要的工作。请把这一目的置于个人实现偏好、贡献规模或争取合并之上。遵循[拉取请求模板](https://github.com/open-webui/open-webui/blob/main/.github/pull_request_template.md)，以 `dev` 为目标分支，完成贡献者许可协议，并在 **Maintainer Request** 部分链接维护者的邀约。遵循现有模式，记录验证过程，并**严格保持在约定范围内**。如果需要调整方案，请回到讨论中沟通，并接受审查可能导致重写或决定不再推进的结果。邀约并不授权进行无关变更或未经邀约的测试，也**不保证一定接受**。对于 i18n/本地化 PR，请说明工作仅限于本地化；这项长期例外认可语言知识的价值，可在现有翻译体系内帮助用户。它不适用于随翻译捆绑的无关行为、重构或依赖。尊重这些边界，包括接受关闭提交的决定，也是参与贡献的一部分。重新打开已被拒绝的 PR，或将其拆成较小提交以寻求不同结果，都违背了这一目的。

### 改进文档 {#improve-documentation}

通过改进文档、编写教程或创建设置指南，帮助更多人轻松使用 Open WebUI。文档位于 [docs 仓库](https://github.com/open-webui/docs)。

### 翻译界面 {#translate-the-ui}

仅限于 i18n/本地化的 PR 不需要维护者邀约。Open WebUI 在 `src/lib/i18n/locales` 中使用 JSON 翻译文件。每个子目录均以 [ISO 639 语言代码](http://www.lingoes.net/en/translator/langcode.htm)命名（例如 `en-US`、`fr-FR`）。

如果你是 Open WebUI 已支持语言的母语使用者，修正现有翻译与新增翻译同样受欢迎。当你的语言中某个标签读起来错误、不自然或用词不当时，请在该语言的 `translation.json` 中修正，并提交仅包含这些变更的 PR。

添加新语言的步骤：

1. 在 `src/lib/i18n/locales` 下新建一个目录，以相应的语言代码命名
2. 将每个语言区域唯一持有的 `en-US/translation.json` 文件复制到新目录
3. 翻译每个 JSON 文件中的字符串值，同时保留对象结构
4. 在 `src/lib/i18n/locales/languages.json` 中注册该语言，然后运行 `npm run i18n:parse`；该命令会根据源字符串重新生成每个已注册语言区域的 `translation.json`，并对其进行格式化和检查

在 `en-US` 中，许多值为空，因为键本身就是英文文本。对于这些条目，请翻译键并将结果写入值。

### 改进无障碍体验 {#improve-accessibility}

无障碍是良好设计的核心组成部分。请通过 Issues 报告无障碍问题，并附上复现详情。实现维护者邀约的界面变更时：

| 原则 | 应做事项 |
|-----------|-----------|
| **语义化 HTML** | 使用 `<button>`、`<label>`、`<nav>` 等语义元素，而不是通用的 `<div>` 容器 |
| **键盘导航** | 确保所有交互元素无需鼠标即可使用 |
| **ARIA 标签** | 在仅靠语义化 HTML 不足以表达时，添加 [ARIA](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA) 角色和标签 |
| **色彩对比度** | 使用 [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/) 验证对比度 |
| **替代文本** | 为有意义的图片提供描述性 `alt`；装饰性图片使用 `alt=""` |

使用 Lighthouse 或浏览器的无障碍工具测试你的变更。

## 报告问题 {#reporting-issues}

新建 issue 前，请先查看 [Issues 标签页](https://github.com/open-webui/open-webui/issues)。提交时：

- **使用 issue 模板。** 不遵循模板或缺少所要求信息的 issue 将被关闭。
- **附上复现步骤。** 说明你执行了什么操作、预期发生什么以及实际发生了什么。
- **具体描述。** 模糊的报告（“它无法工作”）无法得到有效调查。

:::warning 支持范围
Open WebUI 支持 Docker 部署，但我们假定你熟悉 Docker 基础知识。与反向代理配置、容器网络或主机操作系统设置有关的问题不在项目支持范围内。这些主题请参阅 [Docker 官方文档](https://docs.docker.com/get-started/overview/)。
:::
