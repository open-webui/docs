# 智能体网页搜索与 URL 获取

Open WebUI 的网页搜索已从简单的结果注入发展为完整的**智能体研究系统**。启用**原生函数调用（智能体模式）**后，具备足够能力的模型可以自主探索网络、核实事实并自动跟踪链接。

:::tip 最低模型层级（非持续维护的列表）
智能体网页搜索需要能够可靠调用工具并判断何时深入挖掘的模型。这**并不**意味着必须使用前沿模型，成本低、速度快的模型也完全可以。**GPT-5.6 Luna**、**Gemini 3.5 Flash-Lite**、**MiniMax M3**、**DeepSeek V4 Flash**，或本地运行的 **Gemma 4 31B**、**Qwen 3.6 27B**、**Muse Glimmer 30B** 都能很好地处理此类任务并达到最低要求；截至撰写时，这些模型均已验证可用。只有确实过旧或非常小的模型才难以完成多步骤推理。

**此列表不会持续更新**——追逐每次模型发布既不可能，也没有价值。使用你的提供方提供的任何当前模型即可；无需最新且*最强大*的模型，只要足够新即可。
:::

:::info 集中式工具文档
有关所有内置智能体工具（包括网页搜索、知识库、记忆等）的全面信息，请参阅[**原生/智能体模式工具指南**](/features/extensibility/plugin/tools#built-in-system-tools-nativeagentic-mode)。
:::

## 原生模式与传统 RAG {#native-mode-vs-traditional-rag}

| 功能 | 传统 RAG（默认） | 智能体搜索（原生模式） |
|---------|---------------------------|------------------------------|
| **搜索决策** | Open WebUI 根据提示分析作出决定。 | 由**模型**决定是否需要搜索以及何时搜索。 |
| **数据处理** | 获取所有结果，将其分块并执行 **RAG**。 | 直接返回**摘要**；不进行分块，也不使用向量数据库。 |
| **链接跟踪** | 注入排名靠前结果的摘要。 | 模型使用 `fetch_url` 直接读取**完整页面**。 |
| **模型上下文** | 仅获得相关片段（Top-K 个块）。 | 通过 `fetch_url` 获得**完整文本**，上限由你设置。 |
| **推理** | 模型在系统注入*之后*处理数据。 | 模型可以搜索、阅读、检查，然后再次搜索。 |

## 如何启用智能体行为 {#how-to-enable-agentic-behavior}

要启用这些功能，你的模型需要支持原生工具调用并具备合理的多步骤推理能力——至少需要 GPT-5.6 Luna、Gemini 3.5 Flash-Lite、MiniMax M3、Gemma 4 31B 或本地 Muse Glimmer 30B 这一层级的模型。这些内置系统工具的管理员级配置通过[**集中式工具调用指南**](/features/extensibility/plugin/tools#tool-calling-modes-default-vs-native)进行管理。

1. **全局启用网页搜索**：确保已在**设置 → 网页搜索**（管理员区域）中配置搜索引擎。
2. **启用模型能力**：在**设置 → 模型**（管理员区域）中，选择你的模型并启用**网页搜索**能力。
3. **启用默认功能**：在同一模型设置的**默认功能**下，勾选**网页搜索**。这决定新聊天会话默认是否提供 `search_web` 和 `fetch_url` 工具。
4. **确认原生模式（智能体模式）**：
    * 原生模式是默认的工具调用模式，因此除非模型已切换到 Legacy，否则该模式已经生效。在同一模型设置的**高级参数**下，确保**函数调用**设置为 `Native`（而不是 `Legacy`）。
5. **使用优质搜索引擎**：选择能返回相关且最新结果的提供方。为 LLM 工作流构建的托管提供方通常能返回更好的结果，而 SearXNG 等自托管引擎的结果质量在很大程度上取决于上游引擎和实例配置。
6. **使用优质的工具调用模型**：使用支持可靠原生函数调用的近期模型，并确保上下文足以容纳工具架构和搜索结果。

:::info 改用环境变量配置
上述步骤使用管理员面板，这是推荐方式。如果你通过环境变量管理实例，请使用 `DEFAULT_MODEL_PARAMS: '{"function_calling": "native"}'` 设置全局默认值。没有单独的 `FUNCTION_CALLING_MODE` 变量。有关详细信息，请参阅[集中式工具指南](/features/extensibility/plugin/tools#how-to-enable-native-mode-agentic-mode)。
:::

:::tip 模型能力、默认功能与聊天开关
在**原生模式**（受支持的模式）下，`search_web` 和 `fetch_url` 工具要求既启用**网页搜索**能力，又在模型设置的**默认功能**下勾选**网页搜索**（或在聊天中开启）。缺少任何一项，这些工具都不会被注入，即使其他内置工具可能仍会显示。

这里记录 Legacy 模式的 RAG 式注入行为，仅供旧版部署参考。原生模式是默认模式；Legacy 模式是不受支持的退出选项。

**重要**：如果禁用了模型的 `web_search` 能力，即使你在聊天中手动开启网页搜索，原生模式下也不会提供这些工具。
:::

## 原生工具如何处理数据（智能体模式） {#how-native-tools-handle-data-agentic-mode}

需要理解的是，原生模式（智能体模式）的工作方式与标准模型中的全局“网页搜索”开关有根本区别。

### `search_web`（仅返回摘要） {#search_web-snippets-only}
当模型调用 `search_web` 时：
* **操作**：查询你配置的搜索引擎，并接收标题、链接和摘要列表。
* **结果数量行为**：如果模型省略 `count`，Open WebUI 使用管理员配置的 `WEB_SEARCH_RESULT_COUNT`。如果模型提供 `count`，该值会被限制为不超过同一管理员上限。
* **不使用 RAG**：与传统搜索不同，**不会将任何数据存储到向量数据库中**，也不会进行分块或嵌入。
* **结果**：模型看到的内容与人在搜索结果页面上看到的完全相同。如果摘要中包含答案，模型就会作答；否则，模型必须决定是否“深入查看”某个链接。
* **不是来源**：搜索命中项不会列在引用面板中，模型也不会被要求引用它们。这些页面并未打开，因此没有可引用的内容。结果仍会作为工具输出传递给模型，模型可以像处理其他文本一样，在答案中写出某个链接。

:::info 此版本中的变化
过去，搜索结果会作为引用来源发出，每个命中项对应一个空条目，且全部命名为 `search_web`。模型经常将某个结果的 ID 附加到来自另一个结果的文本上，而面板会将该 ID 解析为一个看似正确的标题，因此错误归因与正确归因无法区分。搜索结果不再作为引用提供。要获得引用，模型必须使用 `fetch_url` 打开页面。

这适用于原生工具调用路径。Legacy 模式仍运行旧版 RAG 式网页搜索，并仍会引用其检索到的内容。
:::

### `fetch_url`（完整页面上下文） {#fetch_url-full-page-context}
如果模型判断搜索摘要信息不足，它将调用 `fetch_url`：
* **直接访问**：该工具访问指定 URL，并使用你配置的**网页加载器**提取正文。
* **原始上下文**：提取的文本会**直接注入模型的上下文窗口**。默认会注入整个页面。要设置上限，请在**设置 > 网页搜索**（管理员区域）中设置**获取 URL 内容长度限制**，或设置 [`WEB_FETCH_MAX_CONTENT_LENGTH`](/reference/env-configuration#web_fetch_max_content_length)；超过该字符数的页面会被截断，并以 `[Content truncated...]` 结尾。
* **文件**：读取之前，Open WebUI 会检查 URL 指向的是网页还是文件。此检查会发送与网页加载器相同的请求，使用相同的 [`USER_AGENT`](/reference/env-configuration#user_agent)、浏览器标头和**验证 SSL 证书**设置，因此阻止未知客户端的网站（例如 Wikimedia）也会以相同方式响应它。随后，PDF 或其他文档会进入文档提取流程，模型将获得其文本。如果文件名没有已知扩展名（例如 `arxiv.org/pdf/1706.03762`），则由服务器报告的文件类型决定文件的读取方式。
* **可引用**：抓取的页面会出现在引用面板中，并以其 URL 作为来源名称。这是网页在原生模式下成为引用的唯一方式，而且该页面必须是模型实际读取过的页面。
* **智能体优势**：由于不使用 RAG，模型可以看到页面的“全貌”，而不是孤立的片段。这使它能够遵循针对特定页面的复杂指令，例如“总结此文档链接中的技术规格表”。

:::tip
通过将 `search_web` 与 `fetch_url` 分开并避免使用 RAG，模型可以充当自己的**信息检索**智能体，精确选择哪些来源值得完整阅读。
:::

## 深度研究与交错思考 {#deep-research--interleaved-thinking}

由于模型可以多次调用 `search_web`，并自主决定何时深入挖掘，因此它能够利用**交错思考**执行真正的“深度研究”。这会形成一个强大的研究循环，模型在其中充当自己的研究助手。

### 交错思考的工作原理 {#how-interleaved-thinking-works}

交错思考是模型在连续循环中交替进行**推理**和**行动**的能力。模型不必只搜索一次就作答，而是可以：

<details>
<summary>详细研究循环示例</summary>

**用户提问：**“React 生态系统中有哪些最新的安全漏洞？”

**第 1 步：初步分析**
- 模型思考：“我需要有关 React 安全的最新信息。先进行一次广泛搜索。”

**第 2 步：首次搜索**
```
Model calls: search_web("React security vulnerabilities 2026")
```
- 根据管理员配置的 `WEB_SEARCH_RESULT_COUNT`（或模型提供的较小 `count`）接收摘要
- 看到对 npm 软件包和 CVE 数据库的引用

**第 3 步：差距分析**
- 模型思考：“摘要提到了 CVE，但细节不够。我应该获取某个具体的安全公告页面。”

**第 4 步：定向获取**
```
Model calls: fetch_url("https://example.com/react-security-advisory-2026")
```
- 阅读安全公告全文
- 识别具体的漏洞类型（XSS、注入等）

**第 5 步：细化**
- 模型思考：“我发现了服务器端漏洞。现在专门搜索客户端问题。”

**第 6 步：细化搜索**
```
Model calls: search_web("React client-side XSS CVE 2026")
```
- 获得有关跨站脚本问题的更具体结果
- 识别缓解策略

**第 7 步：综合**
- 模型思考：“我现在已经从多个权威来源获得了全面信息。可以进行综合了。”

**第 8 步：最终回答**
- 提供引用多个来源、详细且有依据的回答
- 包含具体的 CVE 编号、受影响版本和缓解步骤

</details>

### 智能体研究循环 {#the-agentic-research-loop}

模型会持续循环这些阶段，直到获得足够的信息：

1. **思考（THINK）**：分析当前知识差距，确定缺少哪些信息
2. **行动（ACT）**：搜索网页或获取特定 URL，以收集相关内容
3. **评估（EVALUATE）**：评估所检索信息的质量和完整性
4. **决策（DECIDE）**：确定是否需要进一步研究，或是否已经收集到足够的上下文
5. **迭代（ITERATE）**：如果仍有差距，则返回第 1 步，聚焦更精确的方向并使用更具体的查询
6. **综合（SYNTHESIZE）**：收集到足够的信息后，整理并给出最终答案

此循环会自主重复，直到模型掌握全面且经过核实的信息，能够以较高置信度回答你的问题。

### 主要优势 {#key-advantages}

**自适应精确度**：模型并非只搜索一次就接受出现的任何结果，而是会根据发现的内容不断优化搜索策略。如果最初的广泛搜索只返回表层信息，模型会自动转向更具体的技术术语、产品名称、版本号或专业术语。每次迭代都会逐步增强针对性，从一般概念深入到具体细节，确保最终答案既全面又准确。

**深度链接跟踪与发现**：与仅使用搜索结果摘要的传统 RAG 系统不同，模型可以在摘要信息不足时阅读完整页面。更强大的是，**当模型使用 `fetch_url` 阅读页面时，它可以发现并跟踪该内容中提及的新 URL**。例如，如果抓取的页面引用了技术规格文档、官方更新日志或相关研究论文，模型可以自主地再次对这些发现的 URL 调用 `fetch_url`，进一步深入研究。这会形成自然的“网页浏览”行为：模型沿着引用链探索链接资源，并通过阅读多个相互关联的来源建立全面理解，就像人类研究员一样。

**事实核实与交叉引用**：模型可以通过交叉引用多个独立来源自主核实信息。如果某个来源提出一项论断，模型可以搜索权威来源的佐证、比较各官方文档中的版本号，或依据一手来源验证事实。这种多来源核实可以显著减少幻觉并提高答案的可靠性，因为模型会从多样且可信的来源中寻找一致信息，从而建立置信度。

**智能填补差距**：如果初始搜索结果遗漏关键信息或只回答了部分问题，模型会识别这些差距，并使用不同的术语、替代表述或更具体的查询自动进行后续搜索。例如，如果搜索“React performance issues”没有提供某项特定优化技术的信息，模型可能会将搜索细化为“React useMemo optimization”或“React.memo vs useMemo comparison”，以填补知识差距。这确保了对可能需要从多个搜索角度探索的复杂主题进行全面覆盖。

**多来源综合**：模型不会只返回单一来源的信息，而是将多个网页、文档站点、论坛和文章中的见解综合为连贯、全面的答案。这种综合能提供更广泛的背景、兼顾不同观点，并呈现比任何单一来源都更完整的图景。

**根据上下文选择来源**：模型会智能地决定是依赖搜索摘要（当其中包含足够信息时），还是获取完整页面（当需要更深入的细节时）。它还可以判断何时停止研究，在确保彻底性的同时避免不必要的工具调用。这种效率与全面性之间的平衡，使智能体搜索既快速又可靠。

**思考 → 行动 → 思考**的迭代循环会持续进行，直到模型获得足够的信息，能够以最高准确度回答你的请求。
