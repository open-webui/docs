# 提示词缓存（KV Cache）优化

大多数托管 LLM 服务提供方都会缓存请求**前缀**的 KV 状态。当两个请求具有完全相同的前导词元序列时，服务提供方会从缓存中提供共享部分，而不是重新计算，因此成本**更低、速度更快**。如果你希望通过尽可能多地命中缓存来节省费用，本页面正是为你准备的。

:::tip 适用对象
适用于任何希望在支持提示词/前缀缓存的服务提供方上最大限度提高缓存命中率（并降低支出/延迟）的用户，包括 Anthropic、OpenAI、Google Gemini、DeepSeek 和 OpenAI 兼容网关。
:::

:::warning 开始之前
你的模型（或提供该模型的服务提供方/网关）必须**支持提示词缓存**，并且你的请求必须实际**启用**该功能。

- **完全自动**：相同的前导词元会被缓存和复用，无需选择启用，也无需支付额外的启用费用（例如 OpenAI、Gemini、DeepSeek）。通常称为**隐式缓存**或**自动前缀缓存**。
- **按请求选择启用**：只有请求明确提出要求时，服务提供方才会缓存。**Anthropic**同时支持**显式**缓存（缓存断点）和它所称的**隐式**缓存，但两种情况下都必须在**每个请求**中发送缓存指令，而且**缓存写入会计费**，因此绝不会在没有提示的情况下开启。你必须发送该启用指令，缓存才会生效。

如果你的模型或终结点完全不缓存提示词，以下任何设置都不会改变你的成本或延迟。
:::

## 一分钟了解提示词缓存的工作原理 {#how-prompt-caching-works-in-one-minute}

- 服务提供方从请求的**开头**向后缓存。
- 命中缓存要求前缀与之前的请求**完全相同**。
- 请求一旦出现差异，缓存就会**从该位置到末尾**全部失效。

因此，黄金法则是：

> **保持每个请求的开头稳定，只允许在末尾追加新内容。**

聊天对话会自然地在末尾追加新轮次，天然有利于缓存，**除非某些内容在每轮都改写请求的较早部分**。本指南要做的就是消除这些改写。

## 哪些因素会破坏 Open WebUI 中的缓存 {#what-breaks-the-cache-in-open-webui}

Open WebUI 可以在每轮动态插入内容。任何会更改**系统消息**或**较早用户消息**的内容都会使缓存前缀失效。常见来源如下：

| 来源 | 行为 | 缓存影响 |
|---|---|---|
| **预加载文件（Preload files，RAG）** | 每轮检索文件/知识分块，并使用 RAG 模板将其注入最新消息 | 高：注入内容随每次查询变化 |
| **引用（Citations）** | 使用原生函数调用时，将来源标记追加到生成它们的工具结果中，并随该结果一起保存。使用 Legacy 时，每轮通过 RAG 模板将来源添加到你的消息中（设置 `RAG_SYSTEM_CONTEXT` 时添加到系统消息） | 原生模式无影响，请参阅下方说明。Legacy 模式影响高 |
| **记忆（Memory）** | 使用原生函数调用时，每次回复将召回的记忆作为隐藏的 `recall_memories` 工具结果在你的消息之后添加一次。不使用原生函数调用时，每轮将其追加到你的消息中 | 原生模式无影响。Legacy 模式影响高：记忆变化时内容就会变化 |
| **全文（Full text）**开关 | 将整个文件注入每条消息 | 非常高：但它是**预加载文件（Preload files）**的子模式，仅在预加载文件开启时触发 |
| **动态语音模式提示词** | 在系统消息前添加一条简短的语音指令 | 低：语音模式开启期间保持不变 |
| **附件元数据块** | 在消息中以元数据（ID 和名称）形式列出该消息附加的文件、知识库、笔记和聊天 | 低：只要附件不变就保持稳定 |
| **附加知识列表** | 使用原生函数调用时，每次回复将模型或文件夹附加的知识作为隐藏的 `list_attached_knowledge` 工具结果在你的消息之后列出一次。没有内容可列出时跳过 | 无：随回复保存，后续原样重放 |
| **Open Terminal `AGENTS.md`** | 每轮读取终端用户主目录中的 `AGENTS.md`，并将其作为用户消息添加到第一条用户消息之前 | 文件发生变化时，从第一条用户消息开始的所有缓存都会失效，例如模型在聊天中编辑该文件时。系统消息和工具仍保持缓存 |
| **Open Terminal 技能** | 将终端技能添加到技能列表；使用原生函数调用时，该列表是每次回复出现一次的隐藏 `list_available_skills` 工具结果（没有技能时跳过）。使用 Legacy 时，只有所选技能会写入系统消息 | 添加或移除技能的当轮只会改变请求末尾。只有在第一个技能出现或最后一个技能消失时，工具列表才会变化，因为只要至少列出一个技能，就会提供技能工具 |
| **Open Terminal 工作目录** | 每轮将终端的当前工作目录写入命令工具的指令 | 工作目录变化时会改变工具列表。关闭连接的[工作目录上下文](/features/open-terminal/setup/connecting#working-directory-context)以保持稳定 |
| **Open Terminal 用户 Shell 工具** | 默认仅在你自己的 Shell 处于打开状态时添加两个对应工具 | 打开或关闭 Shell 时会改变工具列表。将连接的[用户 Shell 工具](/features/open-terminal/setup/connecting#user-shell-tools)设为 `Always Include` 以保持稳定 |
| **[工具搜索（Tool Search）](/features/extensibility/plugin/tools#tool-search)** | 在系统消息末尾添加固定的 `<available_tools>` 指令，将大型工具排除在工具列表之外，并向列表添加 `search_tools` 和 `call_tool`。模型通过工具调用加载工具的完整定义，再通过 `call_tool` 运行它 | 低：只有已启用工具集发生变化时，指令和工具列表才会改变。加载工具不会改变工具列表。开启 [`TOOL_SEARCH_LIST_TOOLS`](/reference/env-configuration#tool_search_list_tools)（默认）时，每当延迟加载工具集发生变化，指令中的延迟加载工具列表也会改变前缀 |

:::info
附件元数据块特意**只包含元数据**（不含文件内容），因此它能跨轮次保持稳定，不会对缓存造成实质影响。需要关注的是上方会注入内容的项目。
:::

:::info 原生函数调用使引用、记忆、技能和知识列表不进入缓存前缀
开启**引用（Citations）**能力且工具返回来源（`query_chat_files`、`query_knowledge_files`、`view_file`、`view_knowledge_file`、`fetch_url`）时，来源标记会追加到该工具结果并随其保存，因此后续请求会重放相同文本。召回的记忆、技能列表和附加知识列表会作为隐藏工具结果（`recall_memories`、`list_available_skills`、`list_attached_knowledge`），在每次回复中于用户消息之后到达一次。空列表或空召回会被跳过，继续生成的回复也会跳过，因为其已保存的输出中已经包含这些内容。它们会保存在回复输出中，并在后续轮次原样重放。请求中的任何较早内容都不会被改写。

这适用于 Web UI 中使用原生函数调用且模型开启**内置工具（Builtin Tools）**能力的聊天。技能列表还需要开启**技能（Skills）**类别，附加知识列表需要开启**知识库（Knowledge Base）**类别。使用 Legacy 函数调用、在没有 Web UI 会话的 API 请求中，或关闭内置工具时，记忆会在每轮追加到你的消息中，并且不存在技能列表或知识列表。

读取最后一条消息的自定义 Pipe 在召回记忆、附加知识或用户拥有技能时，可能会在该位置看到工具消息。Filter 在添加这些结果之前运行：`inlet` 永远不会看到它们，`request` 则从一次回复的第二次调用开始才能看到它们。
:::

### 为什么注入内容会进入最新的用户消息 {#why-the-injection-goes-into-the-latest-user-message}

这种放置方式是有意设计的，在将其视为需要修复的缺陷之前，值得先理解这一点。

自动检索的设计前提是模型主要关注它正在回答的消息。非常小的本地模型和旧模型在实际使用中确实如此：放在对话较早位置的上下文会被忽略，或因上下文窗口过短、无法容纳全部历史而丢失。如果将检索到的上下文放在正在回答的消息之外的任何位置，这些模型就无法可靠地看到它，这决定了检索究竟有效，还是在没有提示的情况下完全不起作用。

破坏缓存前缀是这项保证的代价；如果另一种选择是模型完全无法使用上下文，那么付出这个代价是值得的。当模型足够大、上下文足够长，能够关注对话中更靠前的材料时，这个代价就不再值得付出。所有前沿模型和大多数当前本地模型都具备这种能力。

因此，这两种能力是两种设计之间的选择，而不是一个功能和一个缺陷：

| | 开启上下文注入 | 关闭上下文注入 |
| :--- | :--- | :--- |
| **检索** | 在模型运行前强制执行 | 按需执行，由模型调用工具 |
| **位置** | 每轮改写并写入最新消息 | 作为工具结果追加到末尾 |
| **前缀缓存** | 每轮失效 | 保留 |
| **适用对象** | 小型和短上下文模型 | 其他所有模型 |

关闭预加载文件并不是规避上述成本的临时办法，而是选择另一种设计，也就是本页面所介绍的设计。

## 缓存最优设置 {#the-cache-optimal-setup}

目标是使用**静态前缀**（系统提示词 + 工具），以**仅追加**方式增长（用户轮次和工具结果），并采用**按需检索**而非自动注入。

### 1. 使用静态系统提示词 {#1-use-a-static-system-prompt}

在模型上配置固定的系统提示词，并避免任何会在每轮重新生成它的内容。这是价值最高的单个可缓存块，请在此处一次性写入你的指令（包括如何引用，见下文）。

### 2. 关闭预加载文件（这会启用文件工具） {#2-turn-preload-files-off-this-is-what-switches-the-file-tools-on}

禁用模型的**预加载文件（Preload files）**能力（使用原生函数调用时默认关闭），并保持**文件上传（File Upload）**启用。附加的文件、知识库、笔记和引用的聊天仍会在携带它们的消息上，通过 `<attached_files>` 块作为**稳定的元数据提供给模型**，但其**内容不再自动检索或注入**。请参阅[预加载文件与内置工具](/features/chat-conversations/rag#preload-files-vs-builtin-tools)。

关闭预加载文件还会使内置文件工具可用，让模型能够自行读取和搜索聊天附件：

| 工具 | 模型使用它执行的操作 |
|---|---|
| `list_chat_files` | 查看附加了哪些文件，包括 ID、文件名、内容类型和大小 |
| `query_chat_files` | 跨附件进行语义搜索，或按 ID 搜索单个文件 |
| `grep_chat_files` | 精确文本搜索，返回匹配行及文件 ID 和行号 |
| `view_file` | 按字符偏移量或行范围读取片段 |

开启预加载文件会移除这些工具，因为内容已经位于对话中。

检索随后变为**按需进行**：模型决定获取什么内容并调用工具。工具结果会追加到对话**末尾**，因此绝不会改写缓存前缀。

:::info 聊天中附加的知识库和笔记仍可使用
关闭预加载文件还会将聊天中附加的任何知识库或笔记重新路由到知识工具路径，因此仍可通过 `query_knowledge_files` 等工具搜索它们。此时，知识工具会[只搜索附加的知识](/features/workspace/knowledge#scoped-access-keeps-things-organized)。

通过 `#` 附加或拖入输入框的**聊天文件夹**，只能通过预加载文件到达模型，后者会从文件夹附加的知识中检索。关闭预加载文件时，请使用 `#` 直接附加文件夹的知识库和文件，或者在文件夹内开始聊天，使其知识通过知识工具提供。
:::

:::info 全文开关是预加载文件的子模式
按文件和按知识设置的**全文（Full text）**开关会将完整文档注入每条消息，是最严重的缓存破坏因素。但它在预加载文件**内部**运行，因此关闭预加载文件（本步骤）**就已经禁用了它**。在预加载文件关闭时开启**全文（Full text）**不会产生任何作用。请保持预加载文件关闭，并使用按需工具进行检索。请参阅[检索模式](/features/workspace/knowledge#retrieval-modes)。
:::

### 3. 关闭引用，并将引用规则移入系统提示词 {#3-turn-citations-off-and-move-citation-rules-into-the-system-prompt}

使用原生函数调用时，**引用（Citations）**不会破坏缓存。关闭它会从工具结果中移除来源标记（请求更小），并移除 UI 中回复下方显示的来源标签；模型仍会收到工具结果本身。

要在没有标记的情况下让回答文本包含引用，请**在系统提示词中添加静态引用指令**。这些指令应基于工具实际返回的内容，即文件名或 URL，而不是编号：

- 将文件和知识中的片段引用为工具结果携带的 `source` 文件名，例如 `(handbook.pdf)`。
- 将网页引用为由 `link` 字段构建的 Markdown 链接，例如 `[example.com](https://example.com/...)`。

由于该指令位于（已缓存的）系统提示词中，因此无需每轮注入即可获得引用。

:::warning 不要在此要求编号引用
只有开启**引用（Citations）**时，`[1]`、`[2]` 形式的编号引用才有效，因为编号来自 Open WebUI 添加到工具结果的 `<source>` 标记。没有任何内置工具会返回编号：文件和知识工具返回 `content`、`source` 文件名和 `file_id`，`search_web` 返回 `title`、`link` 和 `snippet`。在关闭引用时，如果系统提示词要求 `[1]` 风格的引用，模型将没有任何可编号的内容，只能编造编号。
:::

:::info `search_web` 返回搜索结果，而非页面正文
`search_web` 会为每条搜索命中向模型提供标题、链接和摘要，这些是搜索引擎返回的内容。它不会抓取这些页面。当模型需要了解页面实际内容时，会针对链接调用 `fetch_url`。仅根据摘要引用页面，实际上是在引用搜索引擎，因此应要求模型在引用任何具体内容之前先抓取页面。
:::

### 4. 保持智能体式检索 {#4-keep-retrieval-agentic}

在模型上启用**内置工具（Builtin Tools）**，并保持所需类别开启。聊天可以携带的每种资源类型都有对应的内置工具：

| 资源 | 工具 | 类别 |
|---|---|---|
| 附加到聊天的文件 | `list_chat_files`、`query_chat_files`、`grep_chat_files`、`view_file`、`display_file` | **文件（Files）** |
| 知识库，包括聊天所在文件夹的知识 | `query_knowledge_files`、`search_knowledge_files`、`grep_knowledge_files`、`view_knowledge_file`、`display_file`，以及未附加知识时的发现工具 | **知识库（Knowledge Base）** |
| 笔记 | `search_notes`、`view_note` | **笔记（Notes）** |
| 用户的聊天 | `search_chats`、`view_chat` | **聊天历史（Chat History）** |

这需要**原生（Native）**函数调用。内置工具是原生模式功能，不会注入到设为 Legacy 的模型中。

**文件（Files）**类别在四类中条件最严格。以下五项必须全部满足，否则工具会在没有提示的情况下缺失：

1. 模型已启用**文件（Files）**内置类别（默认开启）。
2. 模型的**文件上传（File Upload）**能力已开启。
3. 模型的**预加载文件（Preload files）**能力已**关闭**。
4. 聊天实际至少附加了一个文件。
5. 用户拥有 `chat.file_upload` 权限（管理员始终满足）。

每次调用时，每个工具都会在服务器端重新解析资源并检查访问权限，因此只有模型请求时文件内容才会进入上下文；用户已无法打开的附件会被跳过，而不会被读取。请参阅[内置工具参考](/features/extensibility/plugin/tools#built-in-system-tools-nativeagentic-mode)。

:::tip 保持工具列表本身稳定
工具定义与系统提示词一起位于缓存前缀中，因此在对话中途切换类别、附加技能或启用网络搜索，都会使缓存从该位置开始失效。请按模型决定工具集，而不是按轮次决定。请注意，文件工具会在第一个文件附加到聊天时立即出现，这是该对话中的一次性变化，而不是每轮反复变化。
:::

### 5. 有意识地处理记忆 {#5-handle-memory-deliberately}

使用原生函数调用时，召回的记忆会在每次回复中作为隐藏工具结果在你的消息之后到达一次，并在后续轮次原样重放，因此不会影响缓存前缀。使用 Legacy 时，以及在没有 Web UI 会话的 API 请求中，记忆注入会在每轮追加到你的消息中，并且**不受**预加载文件控制，因此可能反复改变缓存。使用原生函数调用可以避免这种情况。

`ENABLE_MEMORY_SYSTEM_CONTEXT=false` 会关闭所有聊天的自动注入。随后，使用原生函数调用的模型会通过记忆工具**按需**读取记忆，因此请在静态系统提示词中指示模型这样做。请参阅[记忆](/features/chat-conversations/memory)。

### 6. 语音模式通常没有问题 {#6-voice-mode-is-usually-fine}

动态语音模式提示词只会在开头添加一次，并在语音模式处于活动状态时保持不变（语音会话通常会开始一个新聊天），因此不会反复改变缓存。在已有输入消息的聊天中发起的通话，无论是标准模式还是实时模式，都会在第一个语音轮次重新构建一次缓存前缀。可以保持原样；如果需要完全固定的系统提示词，请设置 `ENABLE_VOICE_MODE_PROMPT=false`。

## 结果：稳定且仅追加的请求 {#the-result-a-stable-append-only-request}

采用上述设置后：

- **前缀**：系统提示词 + 工具定义，每轮完全相同 → **已缓存**。
- **正文**通过追加新的用户消息和工具结果而增长 → 只有新增末尾未缓存。
- 任何内容（RAG 模板、来源、引用、记忆、技能和知识列表）都不会改写较早的请求。

:::tip 验证你的命中率
观察服务提供方用量响应中的已缓存词元数（例如缓存读取 / 缓存创建输入词元）。正确的设置会显示缓存部分**随对话长度增长**，而每轮未缓存的输入大致保持不变。
:::

## 服务提供方说明 {#provider-notes}

- **Anthropic**：如开头所述，必须在每个请求中选择启用缓存。稳定的前缀可最大限度增加缓存部分。
- **OpenAI / Gemini / DeepSeek / OpenAI 兼容网关**：自动前缀缓存，无需选择启用。
- **位于 OpenAI 兼容网关（OpenRouter、LiteLLM）之后的 Anthropic 模型**：工具结果上的缓存标记会到达网关，因此前缀在整个工具调用循环中都能保持缓存。

无论哪种情况，要求都相同：**不要在轮次之间改写请求的开头。**

## 总结检查清单 {#summary-checklist}

在**设置 > 模型（Settings > Models）**（管理员区域）中找到模型，点击铅笔（**编辑（Edit）**），然后打开**功能（Features）**和**内置工具（Builtin Tools）**进行设置：

- [ ] 静态系统提示词（不按轮次重新生成）
- [ ] 开启**文件上传（File Upload）**，关闭**预加载文件（Preload files）**，不自动注入内容（这也会禁用**全文（Full text）**开关），**并且**这样会注入文件工具
- [ ] 可选：关闭**引用（Citations）**，将引用规则移入系统提示词
- [ ] 开启**内置工具（Builtin Tools）**，并保持**文件（Files）**、**知识库（Knowledge Base）**、**笔记（Notes）**和**聊天历史（Chat History）**类别启用
- [ ] 将函数调用设为**原生（Native）**（Legacy 模式下不存在内置工具）
- [ ] 记忆：原生函数调用使召回的记忆不进入缓存前缀
- [ ] 保持工具列表跨轮次稳定
