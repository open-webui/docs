## Overview

Open WebUI v0.6+ supports seamless integration with external tools via the OpenAPI servers, meaning you can easily extend your LLM workflows using custom or community-powered tool servers.

In this guide, you'll learn how to launch an OpenAPI-compatible tool server and connect it to Open WebUI through the intuitive user interface. Let's get started!

:::tip Choose a model that can use tools reliably
External tools depend on the model to select a tool, generate valid arguments, and interpret its response. Supporting tool calling does not guarantee doing it well. If a connected and enabled tool is ignored or used incorrectly, **try a stronger model with reliable native tool calling** before assuming the problem is in Open WebUI. This applies to OpenAPI tools, native MCP connections, and MCP tools exposed through `mcpo`.
:::

## Step 1: Launch an OpenAPI Tool Server

To begin, you'll need to start one of the reference tool servers available in the [openapi-servers repo](https://github.com/open-webui/openapi-servers). For quick testing, we'll use the time tool server as an example.

Example: Starting the `time` server locally

```bash
git clone https://github.com/open-webui/openapi-servers
cd openapi-servers

# Navigate to the time server
cd servers/time

# Install required dependencies
pip install -r requirements.txt

# Start the server
uvicorn main:app --host 0.0.0.0 --reload
```

Once running, this will host a local OpenAPI server at http://localhost:8000, which you can point Open WebUI to.

![Time Server](/images/openapi-servers/open-webui/time-server.png)

## Step 2: Connect Tool Server in Open WebUI

Next, connect your running tool server to Open WebUI. There are two ways to register tool servers:

#### 1. Tool servers added by an admin

Admins add shared tool servers that are available to all or selected users across the deployment:

1. Open **Settings > Admin > Integrations** and go to the **Tools** section.
2. Click the plus button to add a new tool server.
3. Enter the URL where your OpenAPI tool server is running (for example `http://localhost:8000`).
4. Click **Save**.

![Settings Page](/images/openapi-servers/open-webui/settings.png)

Requests to these servers are sent by the Open WebUI backend, so the backend must be able to reach the URL. `localhost` means the backend server. If the backend runs in Docker, `localhost` inside the container does not reach your host machine, so use `host.docker.internal` or the machine's actual IP instead. Only expose endpoints that are safe to be used by multiple users.

#### 2. Tool servers added in Tether

Users add their own tool servers in the Tether app. They are visible only to the user who added them, run on that user's computer through Tether and show under **Your devices** in the **Tools** list of the **+** menu. See [Your Own Connections](/ecosystem/tether#your-own-connections).

### Optional: Using a Config File with mcpo

If you're running multiple tools through mcpo using a config file, take note:

Each tool is mounted under its own unique path!

For example, if you're using memory and time tools simultaneously through mcpo, they'll each be available at a distinct route:

- http://localhost:8000/time
- http://localhost:8000/memory

This means:

- When connecting a tool in Open WebUI, you must enter the full route to that specific tool. Do NOT enter just the root URL (http://localhost:8000).
- Add each tool individually under **Settings > Admin > Integrations** using their respective subpath URLs.

![MCPO Config Tools Setting](/images/openapi-servers/open-webui/mcpo-config-tools.png)

Good:

http://localhost:8000/time
http://localhost:8000/memory

Not valid:

http://localhost:8000

This ensures Open WebUI recognizes and communicates with each tool server correctly.

---

:::info Forward cookies

**Advanced > Forward cookies** decides whether the cookies from the browser request are sent on to this server. It is off by default.

Turn it on only for a server you control that authenticates the person behind the request by cookie, typically one sitting inside your own network behind the same sign-on. Everything the browser holds for your Open WebUI domain goes with the request, session cookie included, so a third-party endpoint should never have this on.

**This changed:** connections using the **Session** or **System OAuth** auth types used to forward cookies unconditionally. They no longer do. If such a connection stops authenticating after an upgrade, switch this on.

:::

## Step 3: Confirm Your Tool Server Is Connected

While tools are selected for the chat and **Show Input Selections** is on in **Settings > Interface**, a tool indicator shows beside the **+** button in the message input:

![Tool Server Indicator](/images/openapi-servers/open-webui/message-input.png)

Clicking this icon opens a popup where you can:

- See the tools selected for the chat and the tool servers they come from
- Expand an MCP server to load its tool names and descriptions live
- Check whether each server is connected or shows **Auth required**, and use **Reconnect** to sign in again

To disconnect OAuth for an MCP server, use **Disconnect OAuth** next to the tool under **+ > Tools** in the message input.

Here's what the tool information modal looks like:

![Tool Info Modal Expanded](/images/openapi-servers/open-webui/info-modal.png)

### Global Tool Servers Look Different, And Are Hidden by Default!

If you've connected a Global Tool Server (i.e., one that's admin-configured), it will not appear automatically in the input area.

Instead:

- Global tools are hidden by default and must be explicitly activated per user.
- To enable them, you'll need to open the **+** menu in the message input area, select **Tools**, and manually toggle on the specific global tool(s) you want to use.

Here's what that looks like:

![Global Tool Server Message Input](/images/openapi-servers/open-webui/global-message-input.png)

Important Notes for Global Tool Servers:

- They will not show up in the tool indicator popup until enabled from the **+** menu.
- Each global tool must be individually toggled on to become active inside your current chat.
- Admins can control access to global tools via role-based permissions.

This is ideal for team setups or shared environments, where commonly-used tools (e.g., document search, memory, or web lookup) should be centrally accessible by multiple users.

## (Optional) Step 4: Choosing the Function Calling Mode

Native function calling is the default, so there is nothing to switch on for it. The model uses its own built-in tool calling, which needs a model that genuinely supports it. Some local models claim support and produce poor results, so prefer a model with solid native tool calling if you have the choice.

`Legacy` is the alternative: Open WebUI injects the tool definitions into the prompt and calls tools once before generating. It works with a much wider range of models, at the cost of being limited to that single tool-calling round, where Native keeps calling tools until the model is done.

How to switch modes:

1. Open the chat window.
2. Open **Model controls > Controls > Advanced Params** next to the message input.
3. Set the **Function Calling** parameter. `Default` and `Native` behave identically, `Legacy` selects prompt injection.

![Native Tool Call](/images/openapi-servers/open-webui/native.png)

## Troubleshooting & Tips

### Tools are enabled but the model does not use them correctly

If the model answers without calling a needed tool, invents a tool result, supplies invalid arguments, or stops partway through a task, model capability may be the cause. Open WebUI makes the tools available and executes their calls; the model decides how to use them.

1. Confirm that the tool is enabled in the current chat and that the selected model supports native tool calling.
2. Start a fresh chat with only the tool needed for a simple request, such as asking a time tool for the current time.
3. Repeat the same request with a more capable model, keeping the tool and server configuration the same. If that model succeeds, the original model or its serving configuration is a likely cause. Multi-step workflows may require a stronger model even when simple calls work.

Connection failures, authentication errors, and tool-server errors still need their own troubleshooting; switching models will not repair those. See [Model Requirements & Caveats](/features/extensibility/plugin/tools#model-requirements--caveats) for more on model selection.

### Connection fails immediately after adding the URL

**Check the protocol (HTTP vs HTTPS).** Most local tool servers don't use TLS, so the URL needs to be plain `http://`, for example `http://localhost:8000`.

**Check the port number.** The default port varies by server. For example, uvicorn defaults to `8000`, while Open Terminal defaults to `8888`. Make sure the port in your URL matches the port your tool server is actually listening on.

### Connection fails even though the server is running

**Understand which machine "localhost" refers to.** This is the most common connectivity issue. The backend sends the requests, so `localhost` and `host.docker.internal` follow the [rules for admin-added servers](#1-tool-servers-added-by-an-admin). Make sure the tool server binds to `0.0.0.0` if it runs on another machine.

### General tips

- If you're using remote servers, check firewalls and HTTPS configs.
- To make servers persist across reboots, consider deploying them in Docker or with system services.
- When in doubt, try opening the tool server URL (e.g., `http://localhost:8000/docs`) from the machine that sends the requests, the Open WebUI backend host.
