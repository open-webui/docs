# Sub-agents

Sub-agents let a model hand a focused piece of work to a second agent that runs in parallel, then use the result to continue. The model decides when to delegate by calling the `delegate_task` builtin tool; you do not drive it manually.

A sub-agent is a full chat completion of its own. It runs with the same tools, skills and filters as the chat that spawned it, on the current model or one of the [sub-agent models](/features/workspace/models#capabilities-and-bindings) set on it, works through the task on its own, and hands back its final answer. The work happens in a separate chat that is kept out of your chat list, so the parent conversation stays readable.

Sub-agents are disabled by default. An administrator enables them with the [`ENABLE_SUBAGENTS`](/reference/env-configuration#enable_subagents) environment variable or the **Settings > Sub-agents** (admin section) toggle. They are off by default because every delegation is an extra model call, and a single reply can start several at once.

## What a Sub-agent Is Told

A sub-agent builds its instructions the way a new chat message does, starting from the parent chat's original setup: the chat's own system prompt (from **Model controls > Controls** or your **Settings**), the model's system prompt, the chat's variables and the full text of any skills mentioned in the message. The folder's system prompt, tool server and terminal instructions are applied for the sub-agent's own run, along with the [sub-agent system prompt](#admin-limits).

A background sub-agent's result continues the parent chat with instructions built the same way.

## Why Delegate

Delegation buys focus and parallelism:

![Sub-agent settings](/images/admin/admin-subagents.png)

- **A clean context per task.** The sub-agent gets the task and only the context handed to it, instead of the whole conversation, so a long chat does not dilute the work.
- **Real parallelism.** When a model requests several delegations in one reply, they run at the same time rather than one after another.
- **A short answer back.** Only the sub-agent's final result returns to the parent chat. The intermediate tool calls, searches and dead ends stay in the sub-agent's own chat.

Typical uses are researching several questions at once, working through a task that needs many tool calls, and doing a self-contained job whose intermediate steps do not belong in the main thread.

## Foreground and Background

In a saved chat, sub-agents run in the **background**. The model gets the sub-agent's chat ID right away and carries on. When the sub-agent finishes, its result is posted back into the parent chat and **the chat continues on its own, without you sending anything**. The result appears as a collapsible row reading **Sub-agent finished**, **Sub-agent stopped** or **Sub-agent failed**, then the task's title and how long it ran, with an **Open thread** button. If the parent chat is busy at that moment, the result waits and is delivered when the chat is free.

In a channel and in an automation run, sub-agents run in the **foreground**: the reply waits for the sub-agent and receives its answer as the tool result, the same as any other tool call.

### Following Sub-agents

The **Status** button in the chat's top bar shows the chat's context usage and ID, and under **Threads** its sub-agents and scheduled [timers](/features/chat-conversations/chat-features/timers). A running sub-agent shows a spinner, one waiting for you to approve a tool shows a dot, and finished ones are collapsed under **done**. Click a sub-agent to open its chat in a tab, or **Stop** it. **Cancel** removes a timer before it fires.

### Messages Between Chats

With sub-agents on, the model in a saved chat also gets the `send_message` tool. It sends a message to another of your chats: a sub-agent, the chat that started it, or any other chat of yours. A chat that is working reads the message between its tool calls, and an idle one wakes up and replies to it. The message shows in the receiving chat as a row with the sending chat's title and an **Open thread** button. A chat that is waiting for you to approve a tool does not take messages.

## Handing Over Files

A sub-agent starts with no attachments. Nothing the parent chat has uploaded travels with the task on its own, so delegating does not quietly drag every file in a long conversation into a second model call.

To pass a file, the model names it in the `file_ids` argument of `delegate_task`. Those files are attached to the sub-agent's opening message the way you would attach them yourself: an image is handed to the model as an image, so a vision model can actually look at it, and a document is available to the sub-agent exactly as it is in a normal chat, injected when **Preload files** is on or read with the **Files** builtin tools when it is off.

Only files already attached in the parent chat can be passed, and every ID is checked before anything runs. If one of them is unknown or no longer available, the call comes back as `Error: file_ids not attached or unavailable: <ids>` and no sub-agent is started.

A file ID written into `context` is only text. The sub-agent receives the ID and no file, so anything it has to open belongs in `file_ids`.

## Enable Sub-agents

Sub-agents need four things to line up:

1. **Globally enabled**: [`ENABLE_SUBAGENTS`](/reference/env-configuration#enable_subagents), or **Settings > Sub-agents** (admin section).
2. **Enabled for the model**: the **Sub-agents** category under **Builtin Tools** in **Settings > Models > Edit** (admin section) (or **Workspace > Models** for your own model), on by default once the feature is on.
3. **The user's permission**: the **Sub-agents** switch under **Features** in the [default and group permissions](/features/authentication-access/rbac/permissions#4-features-permissions), or [`USER_PERMISSIONS_FEATURES_SUBAGENTS`](/reference/env-configuration#user_permissions_features_subagents). Users without it get none of `delegate_task`, `timer` and `send_message`.
4. **Native function calling in a saved chat**: `delegate_task` is a builtin tool, so it needs Native mode and a request that carries a `session_id`, as every chat started in the interface does. It is not offered in legacy function calling or in temporary chats.

Admins always pass the permission check.

## Admin Limits

Configure these in **Settings > Sub-agents** (admin section), or with the matching environment variables:

| Setting | Variable | Default | Purpose |
|---|---|---|---|
| Max concurrent | [`SUBAGENTS_MAX_CONCURRENT`](/reference/env-configuration#subagents_max_concurrent) | Empty (unlimited) | Foreground sub-agents (channels and automations) at once. Extra ones wait for a slot. |
| Max background | [`SUBAGENTS_MAX_ASYNC`](/reference/env-configuration#subagents_max_async) | Empty (unlimited) | Background sub-agents (saved chats) at once. Extra ones are refused immediately. |
| Max iterations | [`SUBAGENTS_MAX_ITERATIONS`](/reference/env-configuration#subagents_max_iterations) | Empty (unlimited) | Tool-call rounds one sub-agent may run. At the limit it writes a final answer without tools, and that answer goes back to the parent. |
| Max output | [`SUBAGENTS_MAX_OUTPUT`](/reference/env-configuration#subagents_max_output) | Empty (unlimited) | Characters returned to the parent. Longer results are truncated. |
| System prompt | [`SUBAGENTS_SYSTEM_PROMPT`](/reference/env-configuration#subagents_system_prompt) | Built-in | Added on top of the model's own system prompt. |

Three limits are worth understanding before changing them:

- **They count per worker process, not per deployment.** With multiple workers or replicas, the real ceiling is the limit multiplied by the number of processes.
- **Max concurrent only takes effect at startup.** It is read when the first delegation runs and is not re-read afterwards, so changing it needs a restart. Max background applies immediately.
- **A limit is a positive whole number.** Empty or `0` means no limit. Use [`ENABLE_SUBAGENTS`](/reference/env-configuration#enable_subagents) to turn the feature off.

## What a Sub-agent Cannot Do

Sub-agents are narrower than the chat that starts them:

- **No recursion.** A sub-agent cannot delegate again or set timers, so delegation cannot fan out without bound.
- **No questions to you.** A sub-agent cannot ask you questions. It can still send a message to the chat that started it.
- **No memory writes.** It can read memories but cannot add, change or delete them, keeping delegated work from quietly rewriting your personalization.
- **No code interpreter in the background**, unless the engine is Jupyter, since the browser-based Pyodide engine needs a live session.
- **Sub-agent targets.** The **Sub-agents** list offers the instance's own models.
- **Tether tool servers only while the device is online.** A sub-agent inherits the chat's tool servers, including the ones you added in Tether, and those resolve only while the Tether device is connected.

Each sub-agent runs in its own chat. These chats are hidden from chat lists and search, and are deleted together with the parent chat. Admins can read them by id even with [`ENABLE_ADMIN_CHAT_ACCESS`](/reference/env-configuration#enable_admin_chat_access) off.

## Cost

Every delegation is another full chat completion, with the same tools, and may loop up to the iteration limit. One reply can start several at once, and each background result restarts the parent chat to process it, which is another turn.

No limits are set by default, so only the model decides how many sub-agents run and how long they loop. On a metered API, set the [Admin Limits](#admin-limits).

What delegation costs shows up in [Analytics](/features/administration/analytics) next to everything else.

## Managing Sub-agents from Chat

### Available tools

| Tool | Purpose |
|---|---|
| `delegate_task` | Delegate a task to a parallel sub-agent. |
| `send_message` | Send a message to another of the user's chats, such as a sub-agent or the chat that started it. |

`delegate_task` takes the `task` to perform, optional `context` to carry across (decisions, file paths, findings), optional `file_ids` naming attachments the sub-agent has to open (see [Handing Over Files](#handing-over-files)), `model_id` to pick one of the model's sub-agent models, and a short `title` for the task, which names the sub-agent's chat. `send_message` takes the `chat_id` of the receiving chat and the `message`.

The **Sub-agents** list in the model editor gives the parent model additional targets it can choose. When a `delegate_task` call omits `model_id`, the sub-agent runs on the current model even if the list contains other models.

If the expected target is missing, check that the target is configured on the parent model and available to the user running the chat. Open WebUI offers only configured targets the user can access. If no targets qualify, the tool omits the `model_id` parameter. If a call explicitly names an unavailable target, it returns an error.

:::info The Sub-agents category also controls timers
The `timer` tool is injected by the same category and the same [`ENABLE_SUBAGENTS`](/reference/env-configuration#enable_subagents) toggle. Turning sub-agents off also removes timers.
:::
