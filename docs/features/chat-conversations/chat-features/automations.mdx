# Automations

Automations let you schedule prompts to run automatically at recurring times. By default each run creates a chat and executes through the normal chat completion pipeline, so model defaults, tools, filters, and other pipeline behavior still apply.

Runs use [memory](/features/chat-conversations/memory) the same way your chats do. When memory is on for you, a run gets the memory tools and, with **Memory System Context** on, your stored memories in its context, under the same model, permission and admin settings as a chat. Whether memory is on follows your **Memory** switch in **Settings > Personalization**; if you never set it, the [default interface settings](/features/administration/interface-defaults) decide, and without those, whether Memories is enabled for the instance.

Automations can be enabled or disabled globally by an administrator via the [`ENABLE_AUTOMATIONS`](/reference/env-configuration#enable_automations) environment variable or the **Settings > General** (admin section) toggle. When disabled, the automation worker stops processing, API endpoints return `403`, and the sidebar entry is hidden.

## What You Can Automate

- Run a prompt on a schedule (hourly, daily, weekly, monthly, custom RRULE)
- Start a run from another service with a [webhook](#webhooks) URL, optionally passing it text
- [Share](#sharing) an automation with users and groups so they can follow its runs
- Trigger a run manually with **Run now**
- Pause/resume automations without deleting them
- Review execution history for each automation
- Optionally file the chats a schedule creates into a [folder](/features/chat-conversations/chat-features/conversation-organization#the-folder-page) you can edit, shared folders included, so a team sees every run in one place
- Give runs a machine and working folder, and run an [agent](/features/open-terminal/agents) from that machine

## Access Control

Automations are permission-gated for non-admin users.

- **Admins**: always have access to Automations
- **Users**: require the **Features > Automations** permission

Every run uses the creator's account, so the creator decides what an automation does. Admins can open every automation. Other people reach an automation through [sharing](#sharing) or a shared [folder](#folders), and an automation that is not shared with them stays hidden. The **Features > Automations** permission decides whether someone may have automations at all.

An administrator cannot pause or delete another user's automation from the interface. To stop a user's automations, set their role to **Pending** or remove their **Features > Automations** permission. Each run then ends as failed with `Owner no longer permitted to run automations`, and the schedule keeps advancing, so runs resume once the role or permission is back.

See [RBAC Permissions](/features/authentication-access/rbac/permissions#4-features-permissions) for the permission category.

To grant user access:

1. Open **Admin Panel > Users > Groups**
2. Edit **Default permissions** or a specific group
3. Enable **Features > Automations**

You can also set this default via [`USER_PERMISSIONS_FEATURES_AUTOMATIONS`](/reference/env-configuration#user_permissions_features_automations).

:::tip Quick Access
Hold **Shift** in the User Menu to reveal pin/unpin buttons. Pinning Automations adds a shortcut icon to the sidebar rail for one-click access.
:::

## Admin Limits

Administrators can set global limits on automation usage for non-admin users. These are configured via environment variables. **Admins bypass the count and interval limits.**

| Setting | Effect | Env Variable |
|---------|--------|--------------|
| **Max Automation Count** | Caps the number of automations a user can create | [`AUTOMATION_MAX_COUNT`](/reference/env-configuration#automation_max_count) |
| **Min Recurrence Interval** | Rejects schedules that run more frequently than the configured interval (in seconds) | [`AUTOMATION_MIN_INTERVAL`](/reference/env-configuration#automation_min_interval) |
| **Max Concurrent Runs** | Caps how many automation runs execute at once on each server process. Further runs wait for a free slot, and a changed value needs a restart | [`AUTOMATION_MAX_CONCURRENT`](/reference/env-configuration#automation_max_concurrent) |

- **Max count** is checked only on creation. Existing automations are not deleted if the limit is lowered.
- **Min interval** is checked on both creation and update. One-time automations (`COUNT=1`) are exempt.
- All three default to empty (no limit). Set to a positive integer to enforce. Max concurrent runs applies to admins too.

## Create an Automation

1. Open **User Menu > Automations**
2. Click **New Automation**
3. Set:
   - **Title**
   - **Instructions** (prompt)
   - **Model**
   - **Schedule**, or **None** for an automation that runs only when you click **Run now** or call its [webhook](#webhooks)
4. (Optional) Choose a **Folder** for the chats the automation creates. The picker lists your own folders; to post into a shared folder, create the automation from that folder's page instead (see [Folders](#folders))
5. Click **Create**

After creation, Open WebUI opens the dedicated automation editor page at `/automations/{id}`.

### Model settings used by a run

For a model backed by an Ollama or OpenAI-compatible connection, runs use the model's **System Prompt** and **Advanced Params**. In **Instructions**, enter the task you want the model to perform. The automation editor has no **Model controls** picker. Runs use the model's [default options](/features/workspace/models#model-controls), including when you choose **Run now**.

A model's **Default Features** can turn on Web Search, Image Generation, or Video Generation for a run when the matching capability and instance setting are both enabled. The **Code Interpreter** switch in **Default Features** only applies to interactive chats.

### Chat titles

When a run creates a chat, its initial title is the automation's saved **Title**. Prompt variables such as `{{CURRENT_DATE}}` expand in **Instructions**. In **Title**, they appear as literal text.

### Giving a Run a Machine

The automation editor has a **Machine** list and, once one is picked, a **Working Directory** field. The run uses that machine and starts in that folder. With the field empty it starts in the machine's default folder. The list appears when at least one machine is available to you, and a machine picked here replaces the one configured on the model.

Without a machine in the editor, a run uses the machine configured on its model. Set that in **Workspace > Models**: edit the model and pick the machine from the **Default machine** field. The list appears when at least one machine is available to you and the model's **Terminal** capability is on, which it is by default.

:::info Terminal limits in automations
Machines, including the limits for channel automations, are described in [Creating Machines](/features/open-terminal/terminals/orchestration/creating-terminals#machine-scope).
:::

### Running an Agent {#running-a-coding-agent}

With a machine picked, the **Model** list also offers the agents that machine reports, named `<agent>/<model>`. Changing the machine or folder reloads the list, and **Create** and **Save** wait for it. An agent automation needs a machine before you can save it. Its results always go to a chat. Before each run Open WebUI checks that the machine and the agent are still available and the run fails if either is gone.

## Edit and Manage

From the Automations list, click an automation to open its dedicated editor page.

The page is the editor. Name and instructions sit at the top, followed by a **Properties** list with **Status**, **Schedule**, **Model**, **Destination**, **Machine** and **Next run**. Click any value to change it in place. A **Save** button appears in the header as soon as something differs from the saved automation. The **Status** switch pauses or resumes the automation straight away without **Save**.

The header also has **Run now**, **Copy link** and a **More** menu with **Duplicate** and **Delete**. **Duplicate** opens the new-automation form pre-filled with the same settings and "(Copy)" added to the name. Nothing is saved until you click **Create**.

Below the properties, **Activity** lists the runs, newest first, each marked **Ran** or **Failed** with its time. Click a run to open its chat. Runs load incrementally as you scroll.

The **Destination** menu has a **Start each run in new chat** switch (**Start each run in new thread** for a channel), on by default. Switch it off and every run continues one ongoing chat or channel thread, so each run sees the earlier runs.

For a channel, **Reply in thread** (on by default) decides where the model answers. With the switch on, each run posts its prompt as a channel message and the answer appears as a reply in a thread under it. With it off, each run posts its prompt and its answer as ordinary top-level channel messages, without a thread.

### Quick delete

Hold **Shift** while the Automations list is open and each automation's menu button and on/off switch turn into a delete button. Clicking it deletes that automation straight away, without asking. Release **Shift** and the menu and switch come back. Deleting from the menu still asks you to confirm. While a button or link you reached with `Tab` has focus, holding **Shift** does not turn the menu buttons and switches into delete buttons, so `Shift+Tab` moves back through the list as usual.

## Export and Import

The Automations list header has a split **Create** button. Its dropdown holds **Import JSON** and **Export JSON**, which move automations between instances or accounts.

**Export JSON** downloads every automation you own as `automations-export-<timestamp>.json`, regardless of the search box or the status filter. Each entry keeps its name, schedule and other settings, folder assignment and enabled state. IDs, timestamps and run history are not written to the file, so an export is a copy of your definitions, not a backup of past runs.

**Import JSON** accepts a `.json` file holding either a bare array of automations or an object with an `automations` key. Anything else is rejected as invalid JSON format.

What import does and does not do:

- Every entry becomes a **new** automation. Nothing is matched against what you already have, so importing the same file twice leaves you with duplicates.
- Entries are **created active** unless the file sets `is_active` to `false`. Importing can therefore start scheduled runs on the target instance right away; disable them first if that is not what you want.
- A folder is kept only if a folder with that ID exists in your own account. Otherwise it is dropped and the automation is imported without one.
- Each entry goes through the normal create path, so schedule validation and the [admin limits](#admin-limits) still apply. The first entry that is rejected, an invalid `RRULE` or a hit against [`AUTOMATION_MAX_COUNT`](/reference/env-configuration#automation_max_count) for example, aborts the rest of the import; entries created before it stay.

## Folders

An automation can post its chats into a folder, so a recurring report or digest lands next to the other work on that topic and the folder's unread badge shows how many runs you have not read yet. Set it with **Destination** in the editor: **New chat** keeps the chats loose, **Folder** lists your own folders and **Channel** posts into a channel instead (see [Channels](#channels)).

A folder's own page works as a home for its automations. Pick **Automations** in the switch in its header (visible to users who have the Automations permission) to open it. The **Automations** section lists the folder's automations with the schedule, the date of the last run (or **Paused** or **Not run yet**) and an on/off switch, and its **New automation** button creates one that starts in this folder. Chats an automation made carry a small clock mark in the folder's list and board.

- An automation can post into any folder its creator can edit, shared folders included. Create it from the shared folder's page; the **Destination** picker lists only your own folders.
- Everyone with access to the folder sees the automation in the list and can read its runs, read-only access included. Anyone who can edit the folder can also run it, pause it and change its name and schedule. The creator keeps control of everything else and of deleting it.
- Runs keep landing in the folder for as long as the creator can still edit it. When the creator loses that access, the next run clears the folder and creates its chat outside any folder, and the automation keeps running.
- The folder is a filing destination: the folder's system prompt and attached knowledge apply to the chat as they do to any other chat there.
- Clearing the folder is a normal edit. Future chats go back to the ungrouped list; chats already created stay where they are.
- Deleting a folder does not delete the automations pointed at it. They lose the folder and keep running.
- Imported automations keep their folder only if a folder with that ID exists in your account; otherwise they are imported without one.

## Webhooks

A webhook gives an automation a URL. Calling it starts a run, so a CI job, a monitoring alert or a Git host can trigger an automation without waiting for a schedule. An automation can have a schedule, a webhook or both, and one with neither runs only with **Run now**.

To add one, open the automation, set **Webhook** to on and **Save**. The URL appears once saved. **Regenerate** creates a new URL and the old one stops working. Use it when a URL has leaked. Only the creator sees the URL and can regenerate it.

- **Text for the run.** Put `{{name}}` placeholders in the instructions, for example `Summarize this alert: {{message}}`. A query parameter of the URL or a field of a JSON body with that name fills the placeholder. A `variables` object in the body works too, and bodies from services such as GitHub or Gitea are read as they are. Placeholders can carry defaults and types like in any [prompt](/features/workspace/prompts); a missing required value, a wrong type or a body that is not a JSON object is answered with `400` and no run starts.
- **Allow GET.** `POST` works by default. Switch **Allow GET** on to also accept `GET`, for services that can only open a link. With it off, a `GET` call is answered with `405`.
- **Limits.** Bodies over 64 KB are answered with `413`. An automation takes 30 calls per minute, and further calls get `429`. A paused automation answers `409`. A successful call answers `202`.

:::warning Anyone with the URL can start the automation
The URL is the credential, so share it only with the service that needs it. The call needs no sign-in, and whoever holds the URL starts a run under the creator's account and decides what text goes into the prompt. Only create webhooks for automations whose instructions are safe to run with untrusted text.
:::

Admins control webhooks with **Automation Webhooks** in **Admin Settings > General**, or [`ENABLE_AUTOMATION_WEBHOOKS`](/reference/env-configuration#enable_automation_webhooks) (on by default). With it off, existing URLs stop working. Creating a webhook needs admin rights or the **Features > Automations** permission, and a webhook stops working when its creator loses that permission.

## Sharing

An automation can be shared with specific users and groups, so a team follows a report without each person creating their own. Use **Share** in the automation's header and pick people and groups, like for other [shared items](/features/authentication-access/rbac/permissions#2-sharing-permissions). Non-admin users need the **Automations Sharing** permission to share.

- **Read** lets people open the automation, see its schedule and read the chats its runs created. The **Shared with me** tab of the Automations list shows automations shared directly with you.
- **Write** adds running it, pausing it and changing its name and schedule.
- Only the creator changes the instructions, model, destination and webhook, because runs always use the creator's account. The creator and admins can share and delete.

Automations that sit in a shared folder follow the folder's access (see [Folders](#folders)).

## Channels

With **Destination** set to **Channel**, a run posts into a [channel](/features/channels) instead of creating a chat. The list shows your channels without direct messages.

- Saving needs write access to a standard channel or membership in a group channel. Users who are not admins also need the **Channels** permission.
- Each run posts the instructions into the channel as a message from you. The model's reply goes into a thread under that message, or into the timeline when the admin **Model Response Mode** is set to **Channel**.
- The model receives only the instructions, not earlier messages from the channel.
- Clicking a run in **Activity** opens the channel.
- Agent automations need a chat destination. Saving one with **Channel** is refused with `Agent automations require a chat destination.`, or with `This machine requires a chat destination.` when the machine comes from a template. That second message also refuses a template machine limited to chats.
- A run fails with `Channel not found` when channels are turned off for the instance, and with `Owner no longer permitted to use channels` when its creator has lost the **Channels** permission.

## Scheduling

Supported schedule modes:

- **Once**
- **Hourly**
- **Daily**
- **Weekly**
- **Monthly**
- **Custom** (`RRULE`)

**Daily**, **Weekly** and **Monthly** are scheduled for the minute you pick in your account's stored timezone. Open WebUI reads the timezone from your browser when you sign in or reload the signed-in app. If the server has no valid timezone for the account, it uses its own local timezone.

If the schedule looks wrong, check your device's timezone and reload Open WebUI to sync it. Make an edit to the automation and click **Save** to recalculate its next run with the updated timezone.

Custom schedules accept standard RRULE syntax. Invalid or exhausted rules are rejected.

To run twice a day, choose **Schedule > Custom** and enter `RRULE:FREQ=DAILY;BYHOUR=8,16;BYMINUTE=0` for 08:00 and 16:00 in your schedule timezone.

In Open WebUI 0.13.4, reopening this schedule can show **Daily** with only the first time. Saving an edit to another field while leaving **Schedule** untouched keeps the stored rule. If you change the time in **Daily**, saving replaces the rule with a single daily time. To change the times in a multi-time rule, select **Custom** and re-enter the complete rule before clicking **Save**.

A few rules about how a custom rule is read:

- **Sub-daily rules snap to the clock.** A `SECONDLY`, `MINUTELY` or `HOURLY` rule with no `DTSTART` is anchored to the clock, so every 5 minutes means `:00`, `:05`, `:10` rather than five minutes after you happened to save it.
- **A `DTSTART` is honored where it is still meaningful.** Give the rule a start time and the schedule counts from there, keeping any phase you intended. If that start lies so far in the past that following it literally would mean walking through more than 100,000 occurrences to reach now, the rule falls back to clock alignment instead of stalling.
- **`INTERVAL` must be a positive whole number.** Zero or a negative value is rejected rather than quietly treated as one.
- **One rule per schedule.** Multiple `RRULE` lines are rejected, and `EXRULE` is not supported at all; build the exclusion into the rule itself.
- Property names are read case-insensitively, so `freq=daily` behaves like `FREQ=DAILY`.

## Notes

- Automations run in the background worker loop on a polling interval.
- Every run records a status (`success` or `error`) and optional error details. A run that replies in a chat is recorded as `success` once the reply has finished. A reply that fails or is cancelled is recorded as `error`, and the run keeps its **View chat** link so you can open the chat.
- To be told when a run fails, subscribe a [notification target](/features/chat-conversations/chat-features/notifications#events) to `automation.run_failed`.
- Deleting an automation also removes its run history.

## Managing Automations from Chat

When using **Native Function Calling Mode** with a capable model, automations can also be created and managed directly from within a chat conversation using builtin tools. This allows you to say things like *"Schedule a daily summary report at 9am"* and the model will create the automation for you.

### Available tools

| Tool | What it does |
|------|-------------|
| `create_automation` | Create a new scheduled automation with a name, prompt, and RRULE schedule, and optionally a folder for its chats. Uses the current chat model. |
| `update_automation` | Update an existing automation's name, prompt, schedule, model, or folder |
| `list_automations` | List your scheduled automations with status, folder, schedule, and next runs |
| `toggle_automation` | Pause or resume a scheduled automation |
| `delete_automation` | Delete a scheduled automation and all its run history |

### Requirements

For chat-based automation tools to be available:

1. **Native Function Calling** must be enabled for the model
2. **Builtin Tools** capability must be enabled for the model
3. **Automations** category must be enabled in the model's Builtin Tools settings (enabled by default)
4. **`ENABLE_AUTOMATIONS`** must be enabled globally (enabled by default)
5. The user must have the **Features > Automations** permission (admins always pass)

The folder argument these tools accept is a folder ID, and it is checked against the folders you own: a folder that is not yours, or no longer exists, comes back as an error instead of being applied.

- On `update_automation`, omitting the argument or passing a blank string keeps the automation's current folder. Passing `null` clears it. The same applies to `model_id`: a blank value is ignored rather than wiping the automation's model.
- On `list_automations`, omitting the argument or passing a blank string lists across all folders.

See the [Builtin Tools reference](/features/extensibility/plugin/tools#built-in-system-tools-nativeagentic-mode) for full details on all builtin tools.
