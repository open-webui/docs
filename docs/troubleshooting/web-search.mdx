Web Search in Open WebUI allows language models to access real-time information from the internet. When things don't work as expected, this guide will help you diagnose and fix common issues.

## Common Web Search Issues

### 1. Web Search Fails Behind HTTP Proxy

If you're running Open WebUI behind an HTTP proxy, you might notice that web search queries succeed (e.g., SearXNG returns results), but the subsequent content fetching fails with errors like:

- `[Errno -3] Temporary failure in name resolution`
- `Connection timeout to host`
- `The content provided is empty`

This happens because the web content fetcher doesn't use your `http_proxy`/`https_proxy` environment variables by default.

✅ **Solution:**

1. Navigate to: **Settings > Admin > Tools > Web Search**
2. Enable **Trust Proxy Environment**
3. Save changes

Alternatively, set the environment variable [`WEB_SEARCH_TRUST_ENV`](/reference/env-configuration#web_search_trust_env):

```bash
WEB_SEARCH_TRUST_ENV=True
```

:::info

This is a **ConfigVar** variable, meaning it can be set via environment variable on startup OR configured through the Admin Panel UI. Once set in the UI, the database value takes precedence over the environment variable.

This setting tells Open WebUI's web content loader to respect the proxy settings from your environment variables (`http_proxy`, `https_proxy`). Without this, even if your search engine works through the proxy, fetching content from the returned URLs will fail.

:::

### 2. 403 Forbidden Errors from SearXNG

If you're using SearXNG and seeing `403 Client Error: Forbidden` in your logs, the JSON format is not enabled.

✅ **Solution:**

Edit your SearXNG `settings.yml` and add `json` to the formats list:

```yaml
search:
  formats:
    - html
    - json
```

Restart SearXNG after making this change.

### 3. Empty Content or Poor Results

If web search returns empty content or poor quality results, the issue is often related to context window size or content extraction.

✅ **Solutions:**

- **Increase context length**: Web pages often contain 4,000-8,000+ tokens. If your model has a 2048-token limit, you're missing most of the content. Increase to 16384+ tokens in **Settings > Admin > AI > Models > Edit** the model **> Advanced Params** (anything below will be subpar for web content).

- **Check result count**: Adjust `WEB_SEARCH_RESULT_COUNT` to control how many results are fetched.

  In Native/Agentic tool calling, if the model omits `count` for `search_web`, Open WebUI uses `WEB_SEARCH_RESULT_COUNT` by default. If the model provides `count`, it is capped at the same admin-configured maximum.

- **Try different loaders**: Configure `WEB_LOADER_ENGINE` to use `playwright` for JavaScript-heavy sites or `firecrawl`/`tavily` for better extraction.

- **Set a real User-Agent**: If results from Wikipedia, Cloudflare-protected sites, or other large publishers come back empty (or as 403s in logs), the default Python `requests`/`aiohttp` UA is being filtered by bot detection. Set [`USER_AGENT`](/reference/env-configuration#user_agent) to a real browser-like string (e.g. `Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/126.0 Safari/537.36`). This affects both web search result fetching and the `fetch_url` tool.

For more details on context window issues, see the [RAG Troubleshooting Guide](./rag).

### 4. Web Search Is Enabled but the Model Does Not Call `search_web`

If the web search engine is configured (for example DDGS with DuckDuckGo as the backend), the model has Web Search enabled, and the per-chat Web Search toggle is on, but the assistant still answers without searching, the issue is usually model capability rather than the search provider.

In Native/Agentic mode, Open WebUI exposes web search as the `search_web` tool. The model must decide to call that tool and return a valid structured tool call. Older, smaller, or weaker local models can miss the tool, ignore it, or produce malformed tool calls even when every Open WebUI setting is correct.

✅ **Solutions:**

- **Use a modern, high-quality tool-calling model** for web-search workflows. Frontier models or large recent open-weight models are much more reliable than older/smaller models for deciding when to search and formatting tool calls correctly. See [Tool Calling Modes: Native vs. Legacy](/features/extensibility/plugin/tools#tool-calling-modes-default-vs-native) for model requirements and recommendations.
- **Confirm Native Function Calling is active** in **Settings > Admin > AI > Models > Edit** the model **> Advanced Params > Function Calling**. Built-in web search tools are Native-mode tools.
- **Check all three web-search gates**: Web Search is enabled globally, Web Search is enabled on the model, and the Web Search toggle is enabled in the chat.
- **For DDGS/DuckDuckGo setups**, verify the provider configuration separately using the [DDGS provider guide](/features/chat-conversations/web-search/providers/ddgs), but switch models if DDGS returns results in logs while the assistant never calls `search_web`.

### 5. Connection Timeouts

If web searches are timing out:

✅ **Solutions:**

- **Reduce concurrent requests**: Set `WEB_SEARCH_CONCURRENT_REQUESTS=1` for sequential execution (required for Brave free tier).

- **Adjust loader concurrency**: Lower `WEB_LOADER_CONCURRENT_REQUESTS` if fetching many pages simultaneously.

- **Check network connectivity**: Ensure Open WebUI can reach both the search engine and the result URLs.

## Environment Variables Reference

For a comprehensive list of all web search environment variables, see the [Environment Configuration documentation](/reference/env-configuration#web-search).

Key variables:

| Variable | Description |
|----------|-------------|
| `WEB_SEARCH_TRUST_ENV` | Enable proxy support for content fetching |
| `WEB_SEARCH_RESULT_COUNT` | Number of search results to fetch |
| `WEB_SEARCH_CONCURRENT_REQUESTS` | Concurrent requests to search engine |
| `WEB_LOADER_CONCURRENT_REQUESTS` | Concurrent page fetches |
| `WEB_LOADER_ENGINE` | Content extraction engine |

All of these are persisted settings, so **Settings > Admin > Tools > Web Search** is the live source of truth for them. The page fetcher reads proxy trust, loader concurrency and SSL verification from that saved configuration on each search, so a change you save there applies to the next search without a restart, and matches what the same settings do elsewhere. If a change you made in the admin panel appears not to have taken effect, re-check it there rather than assuming the environment variable is still in charge: the variable seeds the initial value, and the saved setting wins afterwards.
